# disk2glance

Агент для **живого переноса Linux-ВМ в облако OpenStack** (проверено на VK Cloud).
Агент работает внутри исходной ВМ, делает согласованные снапшоты её файловых систем
(на разделах и на линейных томах LVM) и одним потоком отправляет весь диск в **Glance**
(сервис образов OpenStack) как raw-образ. Приложения на исходной ВМ при этом продолжают
работать. Из полученного образа в целевом облаке создаётся новая ВМ.

На исходной ВМ нужны только архив на 2–3 МБ и доступ root. Компилятор, пакеты из
репозиториев и вспомогательные ВМ для переноса не нужны. Модуль ядра загружается только на
время переноса.

## Термины

| Термин | Что это |
|---|---|
| **Исходная ВМ** | ВМ, которую переносят (в любом облаке или на любом гипервизоре). На ней устанавливается и работает агент. |
| **Целевое облако** | облако OpenStack, куда переносят ВМ (проверено на VK Cloud). |
| **Образ** | raw-образ всего диска исходной ВМ в Glance целевого облака, результат работы агента. |
| **Новая ВМ (клон)** | ВМ в целевом облаке, созданная из образа. Копия исходной ВМ на момент снапшота. |
| **Бандл** | архив `disk2glance-<версия>.tar.gz`: агент, установщик, готовые модули ядра, утилиты. |
| **Модуль dattobd** | модуль ядра Linux, который делает снапшоты томов без остановки ФС. Собирается под конкретное ядро. |
| **Сборочная ВМ** | вспомогательная Linux-ВМ, на которой собирают модули dattobd под новые ядра, чтобы добавить их в бандл. В переносе не участвует; нужна только тем, кто сопровождает бандл. |

**Как начать: [docs/quickstart.md](docs/quickstart.md)** — установка и перенос по шагам.

Коротко: архив из [Releases](https://github.com/jaland-hara/disk2glance/releases) скопировать на исходную ВМ, затем

```bash
tar xzf disk2glance-0.5.0.tar.gz && cd disk2glance-0.5.0
sudo ./install.sh                         # создаст /etc/disk2glance/{openrc,props.json,disk2glance.conf}
sudo vi /etc/disk2glance/openrc           # вписать учётные данные целевого облака
sudo disk2glance --check                  # проверка без переноса
sudo disk2glance --detach --name myvm-1   # перенос в фоне, лог: /var/log/disk2glance.log
```

## Состав репозитория

| Путь | Что это |
|---|---|
| `disk2glance.sh` | агент (`/opt/disk2glance/bin/disk2glance`) |
| `disk2s3.sh` | экспериментальный агент для S3 (`/opt/disk2glance/bin/disk2s3`): multipart в несколько потоков |
| `s3restore.sh` | сборка тома из S3 на временной ВМ-сборщике в целевом облаке |
| `install.sh` | установщик и деинсталлятор (офлайн из архива или онлайн по URL) |
| `make-bundle.sh` | сборка `dist/disk2glance-<ver>.tar.gz` |
| `publish-release.sh` | публикация бандла в GitHub Releases (токен из `GITHUB_TOKEN`) |
| `build-module.sh` | сборка `dattobd.ko` под заданные ядра на сборочной ВМ |
| `modules/<ядро>/dattobd.ko` | готовые модули (dattobd 0.12.2) |
| `bin/` | статические `dbdctl`, `update-img` (dattobd) и `jq` 1.7.1 |
| `setup-testload.sh`, `verify-clone.sh` | скрипты проверки: нагрузка на исходной ВМ (PostgreSQL + pgbench + метки времени) и проверка данных на новой ВМ |
| `examples/` | шаблоны `openrc`, `disk2glance.conf` и `props.json` для проверенных ОС |

Учётные данные в репозиторий не попадают. На исходной ВМ они лежат в `/etc/disk2glance/openrc` (600).

## Проверено

**Как проверяли.** Исходные ВМ создавались в VK Cloud из публичных образов (диск 20 ГБ,
ceph-hdd). На каждой работала нагрузка: PostgreSQL с pgbench (40 транзакций/с) и скрипт,
который раз в секунду пишет метку времени в файл и в базу. Во время нагрузки агент
переносил диск в Glance, затем из образа создавалась новая ВМ и проверялись её данные
скриптом `verify-clone.sh`.

| ОС исходной ВМ | Ядро | Откуда модуль dattobd | Загрузка в Glance | Новая ВМ |
|---|---|---|---|---|
| Ubuntu 24.04 | 6.8.0-134-generic | собран на самой исходной ВМ | 222 с, 92 МиБ/с | ✅ |
| RED OS 8.0.3 | 6.12.21-1.red80 | собран на самой исходной ВМ | 222 с, 92 МиБ/с | ✅ |
| RED OS 7.3.7 | 6.1.175-1.el7.3 | собран на самой исходной ВМ | 319 с, 64 МиБ/с (одновременно с другой загрузкой) | ✅ |
| RED OS 8.0.3 | 6.12.92-1.red80 | **из бандла**: собран на сборочной ВМ, на исходную ВМ ничего не компилировали | 262 с, 78 МиБ/с | ✅ |
| RED OS 7.3.7 | 6.1.175-1.el7.3 | из бандла | проверены только установка (из архива и из GitHub Release), `--check` и удаление | — |
| **CentOS 7.9, корень на LVM** (`/boot` xfs, `centos-root` xfs, `centos-swap`) | 3.10.0-1160.119.1.el7 | из бандла (собран на сборочной ВМ CentOS 7) | 480 с, 42 МиБ/с (pgbench без ограничения скорости) | ✅ LVM и XFS подняты, PostgreSQL 9.2 |
| Astra Linux SE 1.7.5 (1.7.5.9) | 6.1.50-1-generic | собран на самой исходной ВМ | 316 с, 64 МиБ/с (одновременно с 1.8.6) | ✅ PostgreSQL 11 |
| Astra Linux SE 1.8.6 (1.8.6.39, обновлена с 1.8.5) | 6.1.166-1-generic | собран на самой исходной ВМ | 462 с, 44 МиБ/с (одновременно с 1.7.5) | ✅ PostgreSQL 15 |

**S3-режим (0.5, экспериментальный).** Ubuntu 24.04, диск 300 ГБ ceph-ssd с 250 ГБ данных:
загрузка в S3 за 17,5 мин (291 МиБ/с, 24 потока), сборка тома из S3 за 19 мин (272 МиБ/с),
новая ВМ загрузилась, данные совпали. Подробности в [docs/s3-mode.md](docs/s3-mode.md).

«✅» означает: новая ВМ загрузилась, файловые системы восстановились по журналу, PostgreSQL
догнал свой журнал (WAL), последняя метка в базе совпадает с моментом снапшота, проверка
индексов (`amcheck`) чистая, суммы балансов pgbench сходятся.
