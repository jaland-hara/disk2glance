# disk2glance

Агент для **живого переноса Linux-ВМ в облако OpenStack** (проверено на VK Cloud).
Агент работает внутри исходной ВМ, делает согласованные снапшоты её файловых систем
(на разделах и на линейных томах LVM) и одним потоком отправляет весь диск в **Glance**
(сервис образов OpenStack) как raw-образ. Приложения на исходной ВМ при этом продолжают
работать. Из полученного образа в целевом облаке создаётся новая ВМ.

На исходной ВМ нужны только архив на 2–3 МБ и доступ root. Компилятор, пакеты из
репозиториев и вспомогательные ВМ для переноса не нужны. Модуль ядра загружается только на
время переноса.

## Варианты поставки

| | 1. Только агент на исходной ВМ | 2. Инфраструктура d2g (экспериментально) |
|---|---|---|
| Что устанавливается | бандл `disk2glance-<версия>.tar.gz` на исходную ВМ | ВМ-оркестратор в целевом проекте (`d2g-server-<версия>.tar.gz`); агент на исходную ВМ — одной командой с оркестратора |
| Куда передаётся диск | образ в Glance (`disk2glance`) или объект в S3 (`disk2s3`, том собирает `s3restore`) | сразу в том Cinder через приёмник |
| Повторные проходы | каждый раз весь диск | дельты: только изменившиеся блоки, по команде или по расписанию |
| Учётные данные на исходной ВМ | учётная запись облака (Glance) или ключ S3 | только сертификат агента |
| Управление | командная строка на исходной ВМ | веб-интерфейс оркестратора и команда `d2g` |
| Новая ВМ | из образа или тома, командами `openstack` | кнопка «Создать ВМ» или `d2g job finish` |
| Инфраструктура в целевом облаке | не нужна | оркестратор с приёмником на той же ВМ; дополнительные приёмники оркестратор создаёт сам |
| Несколько проектов | отдельная учётная запись на каждой исходной ВМ | один оркестратор, учётные записи проектов хранятся только на нём; передача тома в проект или собственный приёмник в проекте |
| Документация | [quickstart.md](docs/quickstart.md), [usage.md](docs/usage.md), [s3-mode.md](docs/s3-mode.md) | [guide.md](docs/guide.md), [orchestrator.md](docs/orchestrator.md), [receiver-mode.md](docs/receiver-mode.md) |


Снапшоты, модули dattobd, проверки гостевой ОС и ограничения у обоих вариантов общие.

## Термины

| Термин | Что это |
|---|---|
| **Исходная ВМ (источник)** | ВМ, которую переносят (в любом облаке или на любом гипервизоре). На ней устанавливается и работает агент. |
| **Целевое облако** | облако OpenStack, куда переносят ВМ (проверено на VK Cloud). |
| **Образ** | raw-образ всего диска исходной ВМ в Glance целевого облака, результат работы агента. |
| **Новая ВМ (клон)** | ВМ в целевом облаке, созданная из образа или тома. Копия исходной ВМ на момент снапшота. |
| **Бандл** | архив `disk2glance-<версия>.tar.gz`: агент, установщик, готовые модули ядра, утилиты. |
| **Модуль dattobd** | модуль ядра Linux, который делает снапшоты томов без остановки ФС. Собирается под конкретное ядро. |
| **Сборочная ВМ** | вспомогательная Linux-ВМ, на которой собирают модули dattobd под новые ядра, чтобы добавить их в бандл. В переносе не участвует; нужна только тем, кто сопровождает бандл. |
| **Оркестратор** | ВМ в целевом проекте (вариант 2): выдаёт агентам сертификаты, создаёт тома и приёмники, ведёт задания, собирает новые ВМ. Управляется через веб-интерфейс и команду `d2g`. |
| **Приёмник** | служба, которая принимает части диска по HTTPS и записывает их в подключённый к ней том Cinder. Приёмник `rx0` работает на ВМ оркестратора, остальные — на отдельных ВМ, которые создаёт оркестратор. |
| **Задание** | перенос одного диска исходной ВМ в один том: том, приёмник, проходы, сборка новой ВМ. |
| **Проход** | одна передача диска со своего снапшота. Первый проход передаёт все непустые блоки, следующие (**дельты**) — только блоки, изменившиеся с прошлого прохода. |
| **Целевой проект** | проект облака, в котором создаётся новая ВМ: проект оркестратора или другой проект, добавленный на вкладке «Проекты». |
| **FIP** | плавающий IP-адрес (floating IP) — публичный адрес, назначаемый ВМ в облаке. |
| **Серый адрес** | частный IP-адрес ВМ во внутренней сети проекта; доступен из той же сети или через Direct Connect. |
| **Флейвор (flavor)** | тип ВМ в облаке: число vCPU и объём памяти, например `STD3-4-8`. |


**Как начать:** вариант 1 (только агент) — [docs/quickstart.md](docs/quickstart.md); вариант 2
(оркестратор и веб-интерфейс) — **[docs/guide.md](docs/guide.md)**, пошаговое руководство с
иллюстрациями.

Коротко (вариант 1, Glance): архив из [Releases](https://github.com/jaland-hara/disk2glance/releases) скопировать на исходную ВМ, затем

```bash
tar xzf disk2glance-0.7.0.tar.gz && cd disk2glance-0.7.0
sudo ./install.sh                         # создаст /etc/disk2glance/{openrc,props.json,disk2glance.conf}
sudo vi /etc/disk2glance/openrc           # вписать учётные данные целевого облака
sudo disk2glance --check                  # проверка без переноса
sudo disk2glance --detach --name myvm-1   # перенос в фоне, лог: /var/log/disk2glance.log
```

Коротко (вариант 2, оркестратор): на ВМ в целевом проекте

```bash
curl -fsSL https://github.com/jaland-hara/disk2glance/releases/latest/download/d2g-server-install.sh | sudo bash
```

далее настройка выполняется мастером в браузере; адрес и одноразовый код выводит установщик
([docs/orchestrator.md](docs/orchestrator.md#установка-оркестратора)).

## Состав репозитория

| Путь | Что это |
|---|---|
| `disk2glance.sh` | агент (`/opt/disk2glance/bin/disk2glance`) |
| `disk2s3.sh` | экспериментальный агент для S3 (`/opt/disk2glance/bin/disk2s3`): multipart в несколько потоков |
| `disk2rx.sh` | агент варианта 2 (`/opt/disk2glance/bin/disk2rx`, служба `disk2rx-agent`): части по HTTPS (mTLS) на приёмник, докачка, дельты, команды оркестратора |
| `server/` | сервер `d2g` (Python, только стандартная библиотека): `d2g/` — оркестратор и приёмник, `install.sh --role orch\|rx`, `unique-boot.sh`, юниты systemd |
| `make-server-bundle.sh` | сборка `dist/d2g-server-<ver>.tar.gz` (сервер + бандл агента для раздачи) |
| `s3restore.sh` | сборка тома из S3 на временной ВМ-сборщике в целевом облаке |
| `install.sh` | установщик и деинсталлятор (офлайн из архива или онлайн по URL) |
| `make-bundle.sh` | сборка `dist/disk2glance-<ver>.tar.gz` |
| `publish-release.sh` | публикация бандла в GitHub Releases (токен из `GITHUB_TOKEN`) |
| `build-module.sh` | сборка `dattobd.ko` под заданные ядра на сборочной ВМ |
| `modules/<ядро>/dattobd.ko` | готовые модули (dattobd 0.12.2) |
| `bin/` | статические `dbdctl`, `update-img` (dattobd) и `jq` 1.7.1 |
| `setup-testload.sh`, `verify-clone.sh` | скрипты проверки: нагрузка на исходной ВМ (PostgreSQL + pgbench + метки времени) и проверка данных на новой ВМ |
| `examples/` | шаблоны `openrc`, `disk2glance.conf` и `props.json` для проверенных ОС |

Учётные данные в репозиторий не попадают. На исходной ВМ они хранятся в `/etc/disk2glance/openrc` (права 600).

## Проверено

**Как проверяли.** Исходные ВМ создавались в VK Cloud из публичных образов (диск 20 ГБ,
ceph-hdd). На каждой работала нагрузка: PostgreSQL с pgbench (40 транзакций/с) и скрипт,
который раз в секунду записывает метку времени
 в файл и в базу. Во время нагрузки агент
переносил диск в Glance, затем из образа создавалась новая ВМ и проверялись её данные
скриптом `verify-clone.sh`.

| ОС исходной ВМ | Ядро | Откуда модуль dattobd | Загрузка в Glance | Новая ВМ |
|---|---|---|---|---|
| Ubuntu 24.04 | 6.8.0-134-generic | собран на самой исходной ВМ | 222 с (3,7 мин), 92 МиБ/с | ✅ |
| RED OS 8.0.3 | 6.12.21-1.red80 | собран на самой исходной ВМ | 222 с (3,7 мин), 92 МиБ/с | ✅ |
| RED OS 7.3.7 | 6.1.175-1.el7.3 | собран на самой исходной ВМ | 319 с (5,3 мин), 64 МиБ/с (одновременно с другой загрузкой) | ✅ |
| RED OS 8.0.3 | 6.12.92-1.red80 | **из бандла**: собран на сборочной ВМ, на исходную ВМ ничего не компилировали | 262 с (4,4 мин), 78 МиБ/с | ✅ |
| RED OS 7.3.7 | 6.1.175-1.el7.3 | из бандла | проверены только установка (из архива и из GitHub Release), `--check` и удаление | — |
| **CentOS 7.9, корень на LVM** (`/boot` xfs, `centos-root` xfs, `centos-swap`) | 3.10.0-1160.119.1.el7 | из бандла (собран на сборочной ВМ CentOS 7) | 480 с (8 мин), 42 МиБ/с (pgbench без ограничения скорости) | ✅ тома LVM активированы, XFS смонтированы, PostgreSQL 9.2 |
| Astra Linux SE 1.7.5 (1.7.5.9) | 6.1.50-1-generic | собран на самой исходной ВМ | 316 с (5,3 мин), 64 МиБ/с (одновременно с 1.8.6) | ✅ PostgreSQL 11 |
| Astra Linux SE 1.8.6 (1.8.6.39, обновлена с 1.8.5) | 6.1.166-1-generic | собран на самой исходной ВМ | 462 с (7,7 мин), 44 МиБ/с (одновременно с 1.7.5) | ✅ PostgreSQL 15 |
| **Ubuntu 24.04 в Яндекс Облаке** (ФС с `discard`) | 6.8.0-146-generic | из бандла (собран на сборочной ВМ) | 704 с (12 мин), 14 МиБ/с (ограничение — скорость чтения диска 10 ГБ); S3: 722 с (12 мин) | ✅ из Glance и из S3 |
| **Ubuntu 22.04 в Cloud.ru** (VPN-шлюз, работал во время переноса) | 5.15.0-181-generic | собран на самой исходной ВМ (`install.sh --build`) | 87 мин, 6 МиБ/с (канал ВМ) | ✅ после исправления настройки сети (см. [guest-drivers.md](docs/guest-drivers.md#3-сеть)) |

**S3-режим (0.5, экспериментальный).** Ubuntu 24.04, диск 300 ГБ ceph-ssd с 250 ГБ данных:
загрузка в S3 за 17,5 мин (291 МиБ/с, 24 потока), сборка тома из S3 за 19 мин (272 МиБ/с),
новая ВМ загрузилась, данные совпали. Подробности в [docs/s3-mode.md](docs/s3-mode.md).

«✅» означает: новая ВМ загрузилась, файловые системы восстановились по журналу, PostgreSQL
применил журнал предзаписи (WAL), последняя метка в базе совпадает с моментом снапшота,
проверка индексов (`amcheck`) ошибок не выявила, суммы балансов pgbench сходятся.

## Планы


Windows 10 (VSS, vTPM/BitLocker), Astra с включённой ЗПС (подпись модуля),
CI для сборки модулей, хуки `--pre-snapshot`/`--post-snapshot` для согласованности
приложений, перенос нескольких дисков за один запуск. Подробнее в [docs/limitations.md](docs/limitations.md).
