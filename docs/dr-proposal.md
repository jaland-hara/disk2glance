# Подсистема DR в оркестраторе: предложение

Проект, не реализовано. Цель: ВМ в ЦОДе или другом облаке постоянно реплицируются в VK Cloud,
а при аварии (или для учений) администратор одной кнопкой поднимает в VK Cloud заранее
описанный набор ВМ из последних реплицированных дисков.

## Что есть сейчас и чего не хватает

Для DR уже есть почти всё:

- **Непрерывная репликация.** Задание с дельтами по расписанию держит том в VK Cloud близким к
  исходной ВМ; дельта передаёт только изменения.
- **Целостная копия после прохода.** Приёмник пишет с `O_DIRECT` и `fdatasync`, а состояние
  «Синхронизировано» ставится только после проверки всех блоков (complete-check). Пока задание
  в этом состоянии и проход не идёт, том — точная копия диска на момент снапшота агента.
- **Защита копии.** На ВМ, поднятой из копии, агент выключен (проверка `product_uuid`) и не
  начнёт передавать данные обратно.
- **Свой приёмник на зону** и **целевые проекты** — тома лежат там, где будут ВМ.

Не хватает трёх вещей:

1. «Создать ВМ» **забирает сам том задания**: после этого репликация по ВМ закончена. Для
   миграции это правильно, для DR — нет: после учений защиту пришлось бы строить заново.
2. Нет **истории**: на томе только последнее состояние. Если исходная ВМ повреждена
   (шифровальщик, ошибка администратора) и повреждение успело уйти дельтой, вернуться некуда.
3. Нет описания **набора ВМ** с порядком запуска, сетями и адресами — сейчас каждую ВМ
   создают вручную.

## Основная идея

Том задания остаётся у приёмника и продолжает принимать дельты. После каждого успешного
прохода оркестратор делает **снапшот тома** в облаке — точку восстановления. ВМ при тесте и
при переключении создаются из **клонов** этих снапшотов, а не из тома задания. Поэтому:

- репликация не прерывается ни учениями, ни переключением (её можно остановить отдельно);
- можно выбрать точку в прошлом, а не только последнюю;
- в Ceph снапшот и клон из него создаются быстро и без полного копирования (проверить на
  стенде, см. ниже).

## Точки восстановления

- **Когда создаются.** Сразу после того, как задание перешло в «Синхронизировано». На время
  создания снапшота (секунды) оркестратор не запускает новый проход этого задания.
- **Что хранится.** Снапшот тома в проекте, где лежит том, с метаданными: `d2g_job`, номер
  прохода, время снапшота агента (момент, которому соответствуют данные).
- **Сколько хранить.** Политика на задание или на план: например, 24 последние точки и по
  одной в сутки за 7 дней. Лишние снапшоты оркестратор удаляет сам.
- **Где видно.** У задания — список точек с временем и возрастом последней.

Снапшот обычной дельты добавляет к месту в хранилище только изменённые блоки; объём точек
стоит показывать в интерфейсе, чтобы следить за квотой и стоимостью.

## План восстановления

План описывает, какие ВМ и как поднимать. Для каждой ВМ:

| Параметр | Пример |
|---|---|
| Задание (источник данных) | `j3fa91c2` — `db01` |
| Имя новой ВМ | `db01-dr` |
| Тип ВМ | `STD3-4-8` |
| Сеть и, при необходимости, фиксированный адрес | `prod-net`, `10.0.10.21` |
| Группы безопасности, ключ | `db`, `ops-key` |
| Группа запуска | 1 |
| Проверка готовности | TCP 5432 открыт, не дольше 10 минут |

ВМ одной группы создаются параллельно; следующая группа стартует, когда все ВМ предыдущей
прошли проверку готовности (или истёк её срок — тогда план останавливается и ждёт решения
администратора). Типичный порядок: базы данных → приложения → веб-серверы.

Для тестового запуска в плане задаются **отдельная сеть** (изолированная, без выхода к рабочим
системам) и при необходимости свои группы безопасности, чтобы копии не конфликтовали с
работающими ВМ и не начали обрабатывать рабочие данные (почта, очереди, интеграции).

## Запуск плана: тест и переключение

**Тест (учения).** Кнопка «Тест»:

1. Для каждой ВМ берётся последняя точка (или выбранная по времени).
2. Из снапшота создаётся том-клон, из него — ВМ в тестовой сети, по группам запуска.
3. Выполняются проверки готовности; ход виден в «Журнале».
4. Репликация всё это время продолжается.
5. Итог — отчёт: время подъёма каждой ВМ и всего плана (фактическое RTO), возраст точек
   (фактическое RPO), результаты проверок.
6. «Завершить тест» удаляет тестовые ВМ и тома-клоны.

**Переключение.** Кнопка «Переключить» (подтверждение вводом имени плана и вторым фактором):

1. Если исходные ВМ доступны (плановое переключение), оркестратор предлагает **последнюю
   дельту**: администратор останавливает приложения, оркестратор запускает проход по всем ВМ
   плана и ждёт его завершения. Если исходные ВМ недоступны — используется последняя точка.
2. Расписание дельт по ВМ плана останавливается.
3. ВМ создаются из клонов в рабочей сети, по группам, с проверками — как при тесте.
4. Тома заданий и точки сохраняются, пока администратор их не удалит: к ним можно вернуться,
   если выбранная точка оказалась неудачной.

Переключение DNS, балансировщиков и внешних адресов на новые ВМ остаётся на стороне клиента;
в плане можно указать FIP для ВМ, если они уже выделены в проекте.

**Возврат (failback)** в первой версии не предлагается: для этого нужен приёмник на стороне
исходной площадки и агент на ВМ в VK Cloud. Это отдельная задача.

## Согласованная точка для группы ВМ

Каждая точка — согласованная копия одной ВМ на момент её снапшота (как после внезапного
отключения питания; согласованность приложений — через хуки `--pre-snapshot` /
`--post-snapshot` агента). У разных ВМ эти моменты разные. Для систем, где ВМ зависят друг от
друга (приложение и база), план может создавать **общую точку**: оркестратор одновременно
запускает дельты всех ВМ плана и делает снапшоты, когда все проходы завершились. Снапшоты агентов
расходятся тогда на секунды, а не на интервал расписания. В интерфейсе общая точка
показывается одной строкой с разбросом времени по ВМ.

## RPO и RTO

- **RPO** (сколько данных можно потерять) — возраст последней точки: интервал расписания плюс
  длительность дельты. Для каждой ВМ плана задаётся целевое RPO; если точка старше, план
  помечается красным в «Обзоре». Позже — уведомления (почта, вебхук).
- **RTO** (сколько длится восстановление) — время подъёма плана. Измеряется на каждом тесте и
  показывается в отчёте; оценка: клон тома — секунды, создание и загрузка ВМ — 1–3 минуты на
  группу, плюс проверки готовности.

## Интерфейс и команды

Новая вкладка «Планы DR»:

- список планов: число ВМ, возраст последней точки и целевое RPO, последний тест и его RTO,
  состояние (защищён / RPO нарушено / идёт тест / переключён);
- редактор плана: ВМ, группы запуска, тип ВМ, сеть и адрес, проверки, тестовая сеть, политика
  точек;
- кнопки «Тест», «Завершить тест», «Переключить»; ход — в «Журнале», отчёты — в карточке плана.

У задания — список точек и «Создать ВМ из точки» (одна ВМ без плана, задание продолжает
работать).

Командная строка:

```bash
sudo d2g point list JOB
sudo d2g plan add NAME | edit NAME | list | show NAME
sudo d2g plan test NAME [--at "2026-10-18 12:00"]
sudo d2g plan test-cleanup NAME
sudo d2g plan failover NAME [--final-delta] [--at TIME]
```

## Ограничения

- **Зона доступности.** Снапшот восстанавливается в том только в своей зоне, поэтому ВМ плана
  создаются в зоне задания. Защиту от отказа целой зоны VK Cloud это не даёт: для этого нужны
  точки в двух зонах, а у агента сейчас одно задание. Подсистема защищает **исходную площадку**.
- **Оркестратор.** План, точки и история лежат в базе оркестратора. Его нужно резервировать
  (выгрузка конфигурации и базы, ВМ оркестратора с бэкапом диска); без оркестратора точки
  остаются в облаке и ВМ можно поднять из них вручную.
- **Режим «передача тома».** Тома с клонами и снапшотами, вероятно, нельзя передавать в другой
  проект средствами Cinder. Для DR в другой проект рекомендуется режим «свой приёмник» — тома и
  точки сразу в целевом проекте.
- **Квоты и стоимость.** Точки занимают место и считаются в квоте снапшотов проекта.
- **Драйверы.** ВМ с VMware и Hyper-V должны быть подготовлены заранее
  ([guest-drivers.md](guest-drivers.md)); тест плана это и проверяет.

## Что проверить на стенде до разработки

1. Снапшот тома, подключённого к приёмнику (`force`), в VK Cloud: разрешён ли, сколько
   длится.
2. Том из снапшота: время создания (клон или полное копирование) для дисков 20, 100 и 500 ГБ,
   разных типов дисков.
3. Квоты на снапшоты и тома, глубина цепочек снапшотов в Ceph при десятках точек.
4. Удаление снапшота, из которого есть клоны (не мешает ли клон удалению старых точек).
5. Передача тома-клона в другой проект.

## Этапы

1. **Точки восстановления**: снапшот после прохода, политика хранения, список в интерфейсе,
   «Создать ВМ из точки» для одной ВМ. Уже это даёт ручной DR и защиту от повреждённых дельт.
2. **Планы**: модель, редактор, тест с отчётом, переключение.
3. **Общие точки плана и контроль RPO** с уведомлениями.
4. Позже: возврат (failback), резервирование оркестратора, точки в двух зонах.
