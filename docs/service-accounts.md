## Зачем отдельная учётная запись

Агент сам обращается к API целевого облака, поэтому пароль учётной записи хранится на исходной
ВМ (`/etc/disk2glance/openrc`) всё время переноса. Личную учётную запись сотрудника для этого
использовать не следует. Рекомендуется **сервисная учётная запись**
(в VK Cloud — СУЗ):

- у неё только те права, которые нужны для переноса, а не все права сотрудника;
- её пароль можно сменить или учётную запись удалить сразу после переноса, не затрагивая других пользователей;
- в журналах облака видно, что действия выполнены именно процессом переноса.

**Рекомендуется несколько сервисных учётных записей**, по одной на группу сотрудников или волну
переноса, например `migr-team-a`, `migr-team-b`, `migr-wave-1`. Тогда:

- пароль, попавший на ВМ одной группы, не даёт доступа к работам другой;
- учётную запись группы, завершившей работы, можно удалить, не затрагивая остальные;
- группе, которой нужно только загружать образы, можно не давать право создавать ВМ.

Сервисная учётная запись принадлежит одному проекту. Для переноса в несколько проектов
создайте по учётной записи в каждом.

## Как создать в VK Cloud

Сервисные учётные записи создаются в разделе управления доступом (IAM) проекта в личном
кабинете; создавать их может владелец проекта, суперадминистратор или администратор
пользователей (IAM). При создании задаются имя, пароль и роли. Роль «Владелец проекта»
сервисной учётной записи назначить нельзя.

Для `openrc` понадобятся (видно на странице «Доступ по API» проекта):

| Переменная | Значение для сервисной учётной записи |
|---|---|
| `OS_USERNAME` | полное имя вида `svc-<ID проекта>-<имя>`, например `svc-9a9b…-migr-team-a` |
| `OS_USER_DOMAIN_NAME` | `service-users` |
| `OS_PASSWORD` | пароль, заданный при создании |
| `OS_PROJECT_ID` | ID проекта |
| `OS_AUTH_URL`, `OS_REGION_NAME` | как у проекта (`https://infra.mail.ru:35357/v3/`, `RegionOne`) |

## Какие роли нужны

Роли VK Cloud ([справочник ролей](https://cloud.vk.ru/docs/ru/access/iam/concepts/roles-reference)),
относящиеся к переносу:

| Роль (техническое имя) | Что даёт по документации VK Cloud |
|---|---|
| «Администратор виртуальных машин» (`mcs_admin_vm`) | полное управление ВМ в Cloud Servers (создание, изменение, удаление) и полное управление сетями в Cloud Network |
| «Младший администратор ВМ» (`mcs_admin_vm_junior`) | то же, но без управления группами безопасности |
| «Администратор внутренних сетей» (`mcs_admin_network_objects`) | сети, подсети, маршрутизаторы, добавление Floating IP в проект |
| «Администратор проекта» (`mcs_admin`) | все ресурсы проекта, кроме групп пользователей и баланса |
| «Оператор ВМ» (`mcs_operator_vm`) | только существующие ВМ: запуск, остановка, консоль; **создавать ВМ не может** |
| «Наблюдатель» (`mcs_viewer`) | только просмотр |

### Что проверено на практике (VK Cloud, октябрь 2026)

| Действие | «Младший администратор ВМ» (`mcs_admin_vm_junior`) | «Администратор виртуальных машин» (`mcs_admin_vm`)* | «Администратор проекта» (`mcs_admin`) |
|---|---|---|---|
| **создать образ в Glance** (то, что делает агент) | **нет**: `403 … add_image` | да | да |
| загрузить данные образа потоком, проверить md5, удалить | — | да | да |
| **полный перенос агентом** (`--check` и диск 20 ГБ) | нет, `--check` останавливается | да (200 с (3,3 мин), 102 МиБ/с) | да |
| просматривать образы проекта и публичные образы | да | да | да |
| импортировать свою ключевую пару | да | да | да |
| создать ВМ из образа: загрузочный том, существующая сеть, существующие группы безопасности | да | да | да |
| создать и удалить группу безопасности | **нет**: `403 create_security_group` | да | да |

\* У проверявшейся учётной записи вместе с `mcs_admin_vm` были роли «Администратор сети»
(`mcs_admin_network`) и «Администратор сетевой безопасности» (`mcs_admin_network_security`).
Они относятся к сетям и ACL, а не к образам, поэтому право на Glance даёт `mcs_admin_vm`.
Проверить конкретную учётную запись можно командой `disk2glance --check`.

### Рекомендуемые наборы

| Что должна уметь учётная запись | Роль |
|---|---|
| **Загрузить образ** (учётная запись для агента на исходной ВМ) | «Администратор виртуальных машин» (`mcs_admin_vm`) — проверено. «Администратор проекта» тоже подходит, но даёт намного больше прав |
| **Создать ВМ из уже загруженного образа** в существующей сети, с существующими группами безопасности | «Младший администратор ВМ» (`mcs_admin_vm_junior`) — проверено |
| то же, плюс создавать и менять группы безопасности | «Администратор виртуальных машин» (`mcs_admin_vm`) — проверено |
| назначить новой ВМ внешний IP (Floating IP) | дополнительно «Администратор внутренних сетей» (`mcs_admin_network_objects`), если основной роли не хватит (не проверялось) |
| **не подходит** для агента | «Младший администратор ВМ», «Оператор ВМ», «Наблюдатель»: создавать образы не могут |

Отсюда следует схема с **двумя видами учётных записей**:

- **учётная запись загрузки** (`mcs_admin_vm`): её пароль размещается на исходных ВМ, через
  неё загружаются образы. Создавайте её на время волны переноса, а после волны удаляйте её
  или меняйте пароль;
- **учётные записи групп** (`mcs_admin_vm_junior`): по одной на группу сотрудников, которые
  создают новые ВМ из загруженных образов в своих сетях. Их пароли на исходные ВМ не попадают,
  а создавать образы и группы безопасности они не могут.

Допускается одна учётная запись `mcs_admin_vm` на группу, если группа сама и загружает
образы, и создаёт ВМ.

`disk2glance --check` всегда проверяет право создавать образы (создаёт и удаляет пустой
тестовый образ), так что неподходящая учётная запись обнаружится до начала переноса:
`ERROR: this account cannot create images in Glance`.

## Учётная запись оркестратора

При переносе через оркестратор ([orchestrator.md](orchestrator.md)) учётная запись облака есть
**только у ВМ оркестратора** (`/etc/d2g/openrc`, права 600). На исходные ВМ попадает лишь
сертификат агента.

Что делает оркестратор в целевом проекте:

| Действие | Зачем |
|---|---|
| создаёт, подключает, отключает и удаляет тома; делает том загрузочным и задаёт свойства образа | том задания и сборка ВМ из него |
| создаёт и удаляет ВМ, читает их состояние | отдельные приёмники и новые ВМ |
| создаёт группу безопасности `d2g-receivers` и правила в ней; при необходимости — группу `d2g-ctl`, которую подключает к своей ВМ | доступ к приёмникам и оркестратору только с нужных адресов |
| назначает свободный FIP из пула отдельному приёмнику и снимает его | приём из интернета напрямую, без прохождения данных через оркестратор (необязательно) |

Подходит роль «Администратор виртуальных машин» (`mcs_admin_vm`): по документации VK Cloud она даёт
управление ВМ, томами и сетями, включая группы безопасности. Для пула FIP может понадобиться ещё
«Администратор внутренних сетей» (`mcs_admin_network_objects`). Новые FIP оркестратор не выделяет.

Мастер установки и форма «Учётная запись облака» проверяют права фактическими операциями:
создают и удаляют том 1 ГБ и группу безопасности. Неподходящая учётная запись выявляется
сразу, до первого переноса. При проверке использовалась та же сервисная учётная запись
проекта, что и в разделе «Что проверено на практике».


## Создание ВМ из образа: что указать

Если учётная запись должна сразу создавать новую ВМ (вручную через CLI или в личном
кабинете), заранее определите:

| Параметр | Где взять | Пример |
|---|---|---|
| сеть (и подсеть) | существующая сеть проекта, в которой будет новая ВМ | `openstack network list` |
| тип ВМ (flavor) | не меньше по CPU/RAM, чем у исходной ВМ | `openstack flavor list` |
| размер загрузочного диска | не меньше размера диска исходной ВМ | `--boot-from-volume 20` |
| тип диска | `ceph-ssd`, `ceph-hdd`, `high-iops` и др. | `openstack volume type list` |
| зона доступности | та же, что у сети и дисков | `openstack availability zone list` |
| группа безопасности | открывает нужные порты новой ВМ | `openstack security group list` |
| ключевая пара (необязательно) | если нужен вход по SSH-ключу, назначенному облаком. **Ключевые пары принадлежат пользователю, а не проекту:** сервисная учётная запись не видит ключи других пользователей (`Invalid key_name`) и должна импортировать свой (`openstack keypair create --public-key key.pub <имя>`) | `openstack keypair list` |

```bash
openstack server create myvm --image <ID образа> --flavor <тип ВМ> \
  --boot-from-volume <ГБ> --network <сеть> --security-group <группа> \
  --key-name <ключ> --availability-zone <зона>
```

Создание новой ВМ средствами самого агента (параметры `--create-vm --network …`) пока не
реализовано.

## После переноса

- Смените пароль сервисной учётной записи или удалите её, если перенос этой группы закончен.
- На исходной и новой ВМ удалите агент вместе с паролем:
  `sudo /opt/disk2glance/install.sh --uninstall --purge`.
