# Сервисные учётные записи VK Cloud для переноса

Термины (исходная ВМ, новая ВМ, целевое облако) объяснены в [README](../README.md#термины).

## Зачем отдельная учётная запись

Агент сам обращается к API целевого облака, поэтому пароль учётной записи лежит на исходной
ВМ (`/etc/disk2glance/openrc`) всё время, пока идёт перенос. Личную учётную запись
сотрудника для этого использовать не стоит. Рекомендуется **сервисная учётная запись**
(в VK Cloud — СУЗ):

- у неё только те права, которые нужны для переноса, а не все права сотрудника;
- её пароль можно сменить или учётную запись удалить сразу после переноса, никого не задев;
- в журналах облака видно, что действия выполнены именно процессом переноса.

**Лучше несколько сервисных учётных записей**, по одной на группу сотрудников или волну
переноса, например `migr-team-a`, `migr-team-b`, `migr-wave-1`. Тогда:

- пароль, попавший на ВМ одной группы, не даёт доступа к работам другой;
- учётную запись завершившейся группы можно удалить, не трогая остальные;
- группе, которой нужно только заливать образы, можно не давать право создавать ВМ.

Сервисная учётная запись принадлежит одному проекту. Для переноса в несколько проектов
создайте по учётной записи в каждом.

## Как создать в VK Cloud

Сервисные учётные записи создаются в разделе управления доступом (IAM) проекта в личном
кабинете; создавать их может владелец проекта, суперадминистратор или администратор
пользователей (IAM). При создании задаются имя, пароль и роли. Роль «Владелец проекта»
сервисной учётной записи назначить нельзя.

Для `openrc` понадобятся (видно на странице «Доступ по API» проекта):

| Переменная | Значение для сервисной учётной записи |
|---|---|
| `OS_USERNAME` | полное имя вида `svc-<ID проекта>-<имя>`, например `svc-9a9b…-migr-team-a` |
| `OS_USER_DOMAIN_NAME` | `service-users` |
| `OS_PASSWORD` | пароль, заданный при создании |
| `OS_PROJECT_ID` | ID проекта |
| `OS_AUTH_URL`, `OS_REGION_NAME` | как у проекта (`https://infra.mail.ru:35357/v3/`, `RegionOne`) |

## Какие роли нужны

Роли VK Cloud ([справочник ролей](https://cloud.vk.ru/docs/ru/access/iam/concepts/roles-reference)),
относящиеся к переносу:

| Роль (техническое имя) | Что даёт по документации VK Cloud |
|---|---|
| «Администратор виртуальных машин» (`mcs_admin_vm`) | полное управление ВМ в Cloud Servers (создание, изменение, удаление) и полное управление сетями в Cloud Network |
| «Младший администратор ВМ» (`mcs_admin_vm_junior`) | то же, но без управления группами безопасности |
| «Администратор внутренних сетей» (`mcs_admin_network_objects`) | сети, подсети, маршрутизаторы, добавление Floating IP в проект |
| «Администратор проекта» (`mcs_admin`) | все ресурсы проекта, кроме групп пользователей и баланса |
| «Оператор ВМ» (`mcs_operator_vm`) | только существующие ВМ: запуск, остановка, консоль; **создавать ВМ не может** |
| «Наблюдатель» (`mcs_viewer`) | только просмотр |

Рекомендуемые наборы:

| Что должна уметь учётная запись | Роли |
|---|---|
| **Только залить образ** (работа агента) | «Администратор виртуальных машин» (`mcs_admin_vm`)* |
| **Залить образ и создать из него ВМ** в существующей сети, с существующими группой безопасности и ключом | «Администратор виртуальных машин» (`mcs_admin_vm`)* |
| то же, плюс назначить новой ВМ внешний IP (Floating IP) | плюс «Администратор внутренних сетей» (`mcs_admin_network_objects`), если `mcs_admin_vm` не хватит |
| запасной вариант, если ролей выше недостаточно | «Администратор проекта» (`mcs_admin`): шире, чем нужно |

\* В документации VK Cloud явно не сказано, какая роль даёт право загружать образы. Образы
относятся к Cloud Servers, поэтому ожидается, что `mcs_admin_vm` достаточно. **Проверьте это
на своей учётной записи до переноса:** `disk2glance --check` создаёт и сразу удаляет пустой
тестовый образ и сообщает `permissions: image create/delete in Glance OK` либо
`this account cannot create images`. Если права не хватает, добавьте роль «Администратор
проекта» или обратитесь в поддержку VK Cloud за более узким набором.

Тестовые переносы, описанные в README, выполнялись под учётной записью с ролью
«Администратор проекта»; минимальный набор `mcs_admin_vm` ещё не проверен на практике.

## Создание ВМ из образа: что указать

Если учётная запись должна сразу создавать новую ВМ (вручную через CLI или в личном
кабинете), заранее определите:

| Параметр | Где взять | Пример |
|---|---|---|
| сеть (и подсеть) | существующая сеть проекта, в которой будет новая ВМ | `openstack network list` |
| тип ВМ (flavor) | не меньше по CPU/RAM, чем у исходной ВМ | `openstack flavor list` |
| размер загрузочного диска | не меньше размера диска исходной ВМ | `--boot-from-volume 20` |
| тип диска | `ceph-ssd`, `ceph-hdd`, `high-iops` и др. | `openstack volume type list` |
| зона доступности | та же, что у сети и дисков | `openstack availability zone list` |
| группа безопасности | открывает нужные порты новой ВМ | `openstack security group list` |
| ключевая пара (необязательно) | если нужен вход по SSH-ключу, назначенному облаком | `openstack keypair list` |

```bash
openstack server create myvm --image <ID образа> --flavor <тип ВМ> \
  --boot-from-volume <ГБ> --network <сеть> --security-group <группа> \
  --key-name <ключ> --availability-zone <зона>
```

Создание новой ВМ средствами самого агента (параметры `--create-vm --network …`) пока не
реализовано.

## После переноса

- Смените пароль сервисной учётной записи или удалите её, если перенос этой группы закончен.
- На исходной и новой ВМ удалите агент вместе с паролем:
  `sudo /opt/disk2glance/install.sh --uninstall --purge`.

Источники: [роли и разрешения VK Cloud](https://cloud.vk.ru/docs/ru/access/iam/concepts/rolesandpermissions),
[справочник ролей](https://cloud.vk.ru/docs/ru/access/iam/concepts/roles-reference).
