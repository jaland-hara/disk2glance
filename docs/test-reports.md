# Протоколы испытаний инфраструктуры d2g

Что и как проверялось на стендах VK Cloud в октябре 2026 года. Как пользоваться продуктом — в
[guide.md](guide.md) и [orchestrator.md](orchestrator.md), скорость — в [speed-tests.md](speed-tests.md).

## Оркестратор и приёмники (16.10.2026)

Оркестратор `d2g-ctl01`: STD3-2-4, PA2, FIP. Источники: Ubuntu 24.04, 20 ГБ ceph-ssd; `src1` с
PostgreSQL + pgbench, `src4` с 10 ГБ данных.

| Проверка | Результат |
|---|---|
| Установка оркестратора из бандла | nginx (SNI), API, CA, `rx0`, `unique-boot.sh` — одной командой |
| `d2g receiver add` | приёмник `rx1` создан за 1 мин 30 с, без ручных действий |
| Установка агента одной командой (серый адрес и FIP оркестратора) | агент загружен с оркестратора, зарегистрирован, `disk2rx-agent` запущен; оркестратор видит реальный адрес источника |
| `d2g job new` для двух агентов | тома созданы и подключены, первый проход запущен автоматически; `src1` выбрал серый IP приёмника, `src4` — SNI через оркестратор |
| Первый проход через отдельный `rx1` | 69 и 56 с |
| Первый проход через `rx0` на ВМ оркестратора (2 vCPU) | 91 и 84 с, ответы «занят» (503): 65–75 — CPU оркестратора загружен полностью |
| Дельта по команде `d2g job sync` | `src1`: 164 МиБ, 60 с; `src4` (+1 ГиБ данных): 1,1 ГиБ, 43 с |
| `d2g job finish` | ВМ `ACTIVE` за ~20 с; новая ВМ `src1` — PostgreSQL восстановился, метка = момент снапшота, `amcheck` ошибок не выявил; новая ВМ `src4` — MD5 данных совпадают, включая файл из дельты |
| Защита от копии | на новой ВМ `src4` агент выключен, идентичность удалена; оркестратор видит только исходную ВМ |
| `d2g job delete`, `d2g receiver delete` | том удалён; приёмник удалён, nginx перенастроен |

## Мастер установки (17.10.2026)

Чистая ВМ `d2g-ctl02` (STD3-2-4, без FIP, доступ через SSH-туннель):

| Проверка | Результат |
|---|---|
| `d2g-server-install.sh --bundle …` | nginx, оркестратор в режиме настройки, выведены адрес, код и отпечаток; `/` перенаправляет на `/setup` |
| Неверный код | отказ, попытка учитывается для блокировки по адресу |
| Шаг 1, TOTP | QR-код отображается, код из приложения проверяется сразу |
| Шаг 2, проверка учётной записи | все проверки пройдены (ВМ видна, том 1 ГБ и группа безопасности созданы и удалены, FIP видны); незаполненные поля и неверная учётная запись приводят к понятному сообщению об ошибке |
| Шаги 3–5 | зона, сеть, адреса, флейвор и тип томов подставлены из облака и метаданных |
| Применить | учётная запись сохранена (600), `d2g setup`, администратор с TOTP, группа `d2g-ctl` открыта и подключена к ВМ, `unique-boot.sh` и `rx0` запущены, оркестратор перезапущен; API мастера после этого отвечает 401 |
| Вход и «Настройки» | вход с паролем и TOTP; изменение доступа и приёмников применяется сразу; список доступа без своего адреса отклонён |

## Из другой площадки: VK Cloud KZ → VK Cloud RU (17.10.2026)

Источник `d2g-kz-src1` в KZ: Standard-4-8, Ubuntu 24.04, диск 100 ГБ ceph-ssd, PostgreSQL + pgbench и
40 ГБ несжимаемых данных. В интернет выходит через роутер (SNAT), FIP у источника нет (SSH через
отдельный jump-хост с FIP). Приёмник — `rx0` на ВМ оркестратора в RU (STD3-4-8). Агент сам выбрал путь
`ctl`: серый адрес приёмника из KZ недоступен.

| Проверка | Результат |
|---|---|
| Первый проход, 8 потоков | 1668 с (28 мин): из 100 ГБ диска по сети 35,3 ГиБ (COW-файл 10 ГБ и пустые блоки не передаются), 21 МиБ/с, 0 повторов; приёмник загружен на 21 % |
| Дельта +5 ГБ: 8 / 24 потока | 16 / 12 МиБ/с — увеличение числа потоков не помогает (при TCP cubic) |
| Канал без протокола d2g (поток по SSH на ВМ оркестратора) | через SNAT роутера KZ: 1 поток 12–15 МиБ/с, 8 потоков вместе 6 МиБ/с; **через FIP (jump-хост): 31 МиБ/с** |
| Последняя дельта (pgbench) | 392 МиБ, 236 с (3,9 мин); почти всё время занимает чтение диска 100 ГБ (433 МиБ/с) |
| ВМ в RU из тома (`job finish`) | загрузилась; PostgreSQL восстановился, последняя метка в файле и в базе = момент снапшота, `amcheck` ошибок не выявил, инвариант pgbench сходится; MD5 всех 5 файлов с данными (40 ГБ) совпадают с источником; агент на копии выключен |

Вывод на момент этого замера: ограничение — выход источника в интернет через роутер, а не
приёмник. Позднее установлено, что основная причина — TCP cubic на канале с потерями: с BBR
тот же путь RU → KZ дал 173–280 МиБ/с (см. раздел «Обратное направление» и
[speed-tests.md](speed-tests.md#1-канал-между-площадками-и-настройка-tcp)). Дельта читает весь диск,
поэтому на больших дисках её время определяет скорость чтения, а не канал.

Замечание: при первой загрузке ВМ `unattended-upgrades` обновил nginx и перезапустил его во время
передачи. Передача через оркестратор продолжилась за счёт повторов (7 повторов частей).
Перезапуски служб d2g и nginx из-за обновления библиотек (`needrestart`) позднее исключены;
обновление самого пакета nginx по-прежнему перезапускает его, это покрывается повторами частей.

## Перенос в другой проект: свой приёмник в VK Cloud KZ (17.10.2026)

Оркестратор `d2g-ctl01` в RU, проект KZ добавлен в режиме «свой приёмник» (сеть `dmz-kz`, без FIP
у приёмника). Источник `kz-src1` (100 ГБ, PostgreSQL + pgbench, 46 ГБ данных) в той же сети KZ.

| Проверка | Результат |
|---|---|
| `d2g target add kz …` | учётная запись KZ прошла проверки; образ Ubuntu 24.04 в KZ найден автоматически |
| `d2g job new kz-src1 --target kz` | оркестратор создал приёмник `rx2` в KZ учётной записью KZ за 2 мин 8 с; приёмник зарегистрировался у оркестратора в RU через интернет (с адреса SNAT роутера KZ) |
| Первый проход | агент сам выбрал серый адрес приёмника внутри KZ: **247 с (4,1 мин), 46 ГиБ, 189 МиБ/с** (через интернет в RU передача того же диска заняла 1529–1668 с (25–28 мин)) |
| Дельта | 352 МиБ, 237 с (4 мин) |
| «Создать ВМ» из интерфейса | форма показала флейворы и сети KZ; ВМ `kz-src1-kz` создана в проекте KZ; PostgreSQL восстановился, метка = момент снапшота, `amcheck` ошибок не выявил, MD5 данных совпали; агент на копии выключен |

Режим «передача тома» реализован, но не проверен: служебная учётная запись стенда видит один проект, а для
проверки нужен второй проект того же региона.

## Обратное направление: VK Cloud RU → оркестратор в VK Cloud KZ (17.10.2026)

Оркестратор с приёмником `rx0` установлен в KZ (`d2g-kz-ctl`, Standard-4-8, FIP), учётная запись —
проекта KZ. Источник `d2g-ru-src1` в RU: STD3-4-8, диск 100 ГБ ceph-ssd, PostgreSQL + pgbench и 40 ГБ
несжимаемых данных, в интернет через SNAT роутера, FIP нет. В группе `d2g-ctl` оркестратора 443
открыт только с адреса SNAT роутера RU.

| Проверка | Результат |
|---|---|
| Установка из бандла на свежий образ Ubuntu KZ | первая попытка завершилась ошибкой 404 при загрузке пакетов nginx: в образе устаревшие списки пакетов. Исправлено: `install.sh` при ошибке выполняет `apt-get update` и повторяет установку |
| Агент по публичному адресу оркестратора | зарегистрировался, путь `ctl` (серый адрес приёмника из RU недоступен, проверка 10 с) |
| Первый проход | 1104 из 1600 частей изменены, по сети 16,4 ГиБ (+ ~12 ГиБ до перезапуска, см. следующую строку), 17–25 МиБ/с; около 49 мин вместе с перезапуском |
| Перезапуск агента посреди прохода | `unattended-upgrades` → `needrestart` перезапустил `disk2rx-agent`. Агент создал новый снапшот и продолжил: приёмник уже имел 543 части, совпадающие блоки не передавались. Исправлено: агент при регистрации исключает себя из перезапусков `needrestart` |
| Дельта (pgbench) | 420 МиБ, 219 с (3,6 мин) |
| Повторный полный проход с BBR (маршрут до приёмника с `congctl bbr`), 16 потоков | **57 ГиБ за 336 с (5,6 мин), 173 МиБ/с** вместо 17–25 МиБ/с с cubic; теперь агент настраивает маршрут автоматически (см. [speed-tests.md](speed-tests.md#1-канал-между-площадками-и-настройка-tcp)) |
| Обе ВМ пересозданы 8-8 с multiqueue на тех же томах (KZ Advanced-8-8, RU STD3-8-8) | оркестратор сохранил настройки; найдено и исправлено: id своей ВМ и `rx0` теперь обновляются при старте, лимит приёмника вычисляется от числа vCPU при запуске (было зафиксировано значение 16 при 4 vCPU), удаление задания с неподключённым томом не ожидает приёмник, `needrestart` больше не перезапускает nginx и службы d2g. Агент на пересозданном источнике определил ВМ как копию и потребовал повторной регистрации |
| Проход RU → KZ 8-8, BBR, 32 потока | **44,8 ГиБ за 256 с (4,3 мин), 260–282 МиБ/с (~2,35 Гбит/с) на данных**, 0 повторов (подробнее в [speed-tests.md](speed-tests.md#коротко)) |
| `d2g receiver add` (отдельный приёмник в KZ) | первая попытка: приёмник не смог подключиться к оркестратору — в `d2g-ctl` не был открыт 443 для приёмников. Исправлено: оркестратор добавляет правило «443 от группы `d2g-receivers`»; повтор — приёмник подключился за 60 с, у него 4 очереди сетевой карты (multiqueue) |
| `job finish` → ВМ в KZ | 51 с до ACTIVE; PostgreSQL восстановился, последняя метка в файле и в базе = момент снапшота, `amcheck` ошибок не выявил, инвариант pgbench сходится, MD5 всех 4 файлов (40 ГБ) совпали; агент на копии выключен |
