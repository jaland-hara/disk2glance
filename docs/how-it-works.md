# Как disk2glance работает внутри гостевой ОС

Термины (исходная ВМ, новая ВМ, бандл) объяснены в [README](../README.md#термины).

## Идея

Агент запускается **внутри работающей исходной ВМ**, то есть той, которую нужно перенести. Он делает
согласованные снапшоты смонтированных файловых систем и одним потоком отправляет **весь
диск** (таблицу разделов, загрузчик, все разделы) в Glance как raw-образ. Приложения на
исходной ВМ в это время продолжают работать и писать. Из образа в целевом облаке
создаётся новая ВМ.

```
                     гостевая ОС исходной ВМ
 ┌───────────────────────────────────────────────────────────────────┐
 │  /dev/vda                                                         │
 │  ├─ [GPT/MBR, промежутки] ────────────── читаются с диска как есть ─┐ │
 │  ├─ vda14 BIOS boot / vda15 EFI ──────── читаются с диска как есть ─┤ │
 │  ├─ vda16 /boot (ext4) ── dattobd ─▶ /dev/datto0 (снапшот) ───────┤ │
 │  ├─ vda1  /     (ext4) ── dattobd ─▶ /dev/datto1 (снапшот) ───────┤ │
 │  └─ [резервная GPT в конце] ─────────── читается с диска как есть ─┤ │
 │                                                                  ▼ │
 │       склейка по смещениям ─▶ md5/sha512 ─▶ curl PUT (chunked) ──────────▶ Glance API
 └───────────────────────────────────────────────────────────────────┘   /v2/images/{id}/file
```

## По шагам

1. **Блокировка и проверки.** Агент работает только от root, второй экземпляр не
   запустится (`flock` на `/run/disk2glance/lock`).
2. **Аутентификация.** Из `/etc/disk2glance/openrc` берутся переменные `OS_*`, затем
   `POST /v3/auth/tokens` в Keystone. Из каталога сервисов в ответе берётся публичный
   адрес Glance для `OS_REGION_NAME`. Токен хранится только в памяти процесса.
3. **Разметка диска** читается из sysfs: `/sys/class/block/vda/vdaN/{start,size}`.
   `sfdisk` не нужен, поэтому агент работает и на CentOS 7. Для каждого раздела
   `findmnt` определяет точку монтирования и тип ФС, по ним выбирается способ чтения:
   - `ext4`, `ext3`, `xfs`, смонтированные: **снапшот dattobd**;
   - всё остальное (BIOS boot, EFI/vfat, swap, несмонтированные разделы): **чтение с диска как есть**;
   - раздел является **LVM PV**: агент разбирает каждый логический том (LV), см. ниже «LVM»;
   - раздел под mdraid или dm-crypt, LV не линейный (thin, raid, striped), группа томов
     на нескольких дисках, btrfs: агент **останавливается с ошибкой** (причины в
     [limitations.md](limitations.md)).
3a. **Проверка гостевой ОС.** Агент проверяет, загрузится ли копия на KVM: драйверы virtio
   в ядре и в initramfs, имена дисков в `/etc/fstab`, наличие cloud-init и гостевого агента.
   Ничего не меняет, только предупреждает ([guest-drivers.md](guest-drivers.md)).
4. **Загрузка модуля.** Если dattobd ещё не загружен, агент выполняет
   `insmod /opt/disk2glance/modules/$(uname -r)/dattobd.ko`. В автозагрузку модуль
   не прописывается.
5. **Снапшоты.** Сначала агент выполняет `sync`, чтобы сбросить на диск накопленные грязные
   данные (почему это важно — см. «Пауза записи при создании снапшота»). Затем для каждого
   устройства из плана (раздела или LV) выполняется
   `dbdctl setup-snapshot [-f <МиБ>] <устройство> <точка_монтирования>/.datto_d2g <minor>`.
   Снапшоты всех устройств делаются подряд, обычно за 1–3 секунды.
   - dattobd перехватывает запись в раздел. Перед тем как блок перезапишется, его старое
     содержимое копируется в **COW-файл** `.datto_d2g` в корне той же ФС.
   - Устройство `/dev/dattoN` всегда отдаёт содержимое раздела на момент снапшота.
   - Размер COW-файла по умолчанию составляет 10% тома, его можно задать параметром
     `--cow-mb`. Если за время переноса изменится больше данных, снапшот перейдёт в
     состояние ошибки: живая ФС при этом не пострадает, но перенос придётся повторить.
   - **TRIM (discard) на время снапшота выключается.** dattobd не сохраняет старые блоки перед
     запросом discard. Если ФС смонтирована с `discard` и диск действительно обнуляет такие
     блоки (так в Яндекс Облаке; Ceph RBD в VK мелкие discard пропускает), файл, удалённый
     после снапшота, попал бы в копию нулями. Поэтому агент перемонтирует такие ФС с
     `nodiscard`, приостанавливает `fstrim.timer` (и не начинает, если `fstrim` уже идёт), а
     после удаления снапшотов возвращает всё как было.
   - COW-файл создаётся на ФС до снапшота, поэтому он попадает и в копию. Чтобы новая ВМ
     не получила лишние гигабайты, агент перед снапшотом кладёт одноразовый юнит
     `/etc/systemd/system/disk2glance-cowclean.service` (включён в `multi-user.target`) и
     сразу после снапшота удаляет его с исходной ВМ. В копии юнит остаётся: на первой
     загрузке новой ВМ он удаляет COW-файлы и сам себя. Без systemd агент предупреждает,
     что файлы `.datto_d2g` на новой ВМ нужно удалить вручную.
6. **Создание образа.** `POST /v2/images` с `disk_format=raw`, `container_format=bare`,
   свойствами из `/etc/disk2glance/props.json` (например `os_distro`, `hw_*`) и служебными
   свойствами `d2g_source_host`, `d2g_snapshot_time`, `d2g_version`.
7. **Поток.** Агент знает, какие байтовые диапазоны диска заняты снапшотированными
   устройствами («наложения»): для раздела это весь раздел, для LV — его экстенты внутри PV.
   Диск читается по порядку смещений (`dd iflag=skip_bytes,count_bytes`, блоками по 4 МиБ):
   диапазоны наложений берутся из `/dev/dattoN`, всё остальное с самого диска. Части
   сшиваются в один поток, который через `tee` проходит через `md5sum` и `sha512sum` и уходит
   в `curl -T - PUT /v2/images/{id}/file` (Transfer-Encoding: chunked). Временных файлов нет,
   поток идёт прямо из памяти в сеть.
8. **Проверка.** Перед ней агент заново получает токен: в VK Cloud токен Keystone живёт час,
   Glance проверяет его только в начале загрузки, и после долгой загрузки старый токен уже
   не годится. Агент сравнивает статус (`active`), размер (байт в байт) и контрольную
   сумму. Если Glance отдаёт `os_hash_value`, сверяется sha512. В VK Cloud его нет,
   поэтому сверяется md5 (`checksum`).
9. **Уборка.** Агент делает `dbdctl destroy` (COW-файлы удаляются) и выгружает модуль, если
   сам его загрузил. Уборка выполняется и при ошибке, и при сигналах INT/TERM/HUP: сначала
   агент останавливает свой конвейер (`dd`, `curl`), потому что `dd`, читающий `/dev/dattoN`,
   не даёт удалить снапшот (EBUSY), затем до пяти раз пытается выполнить `destroy`.
   Только `kill -9` оставляет снапшот: его надо удалить вручную (см. usage.md).

**Запуск вне сессии (`--detach`).** Агент перезапускает себя через
`systemd-run --unit=disk2glance-<дата-время>` с выводом в `/var/log/disk2glance.log`. Так он
не зависит от SSH-сессии. На Astra Linux это обязательно: logind при выходе из сессии
отправляет SIGTERM всем её процессам, и перенос, запущенный через `nohup`, прерывается.

## LVM

Типовая установка CentOS 7 (а также часть RED OS и Astra) выглядит так:

```
/dev/vda1  /boot  xfs                ← снапшот раздела
/dev/vda2  LVM PV (VG centos)
   ├─ centos-root  /     xfs          ← снапшот LV
   └─ centos-swap  swap               ← читается с диска как есть
```

Как агент собирает такой диск:

1. По `/sys/class/block/vda2/holders` находит устройства device-mapper, построенные на
   разделе. По `dm/uuid` проверяет, что это LVM (`LVM-…`), а не dm-crypt или mdraid.
2. Для каждого LV читает `dmsetup table <имя>`. Каждая строка выглядит как
   `<сектор LV> <длина> linear <maj:min PV> <сектор в PV>` и даёт точное соответствие
   экстентов LV местам на диске. Все сегменты должны быть `linear` и лежать на разделах
   этого же диска.
3. Смонтированные LV с ext3/ext4/xfs снапшотируются (dattobd работает с LV так же, как с
   разделом), а их экстенты становятся наложениями в потоке.
4. Метаданные LVM в начале PV, swap, несмонтированные LV и свободные экстенты читаются с
   диска как есть. Метаданные LVM меняются только при операциях с томами
   (`lvcreate`, `lvextend` и т. п.); во время переноса их делать нельзя.

На новой ВМ LVM выглядит точно так же: те же UUID PV и VG, те же имена LV, тот же загрузчик и
initramfs. Поэтому система загружается без изменений.

## Пауза записи при создании снапшота

dattobd создаёт снапшот смонтированной ФС через её заморозку (freeze): ядро сбрасывает на
диск грязные данные, dattobd выделяет COW-файл и включает перехват, после чего ФС
размораживается. Пока ФС заморожена, **запись приложений стоит**.

На простаивающей ФС это занимает 0,1 с. Под сильной нагрузкой на медленном диске пауза
может быть долгой. Замеры на CentOS 7, XFS, ceph-hdd, pgbench без ограничения скорости:

| Вариант | Пауза записи у приложения |
|---|---|
| без подготовки | 17–26 с |
| `sync` перед снапшотом (агент делает это всегда, начиная с 0.3.0) | ~11 с |
| `sync` + `--cow-mb 256` | ~6 с |
| та же исходная ВМ без нагрузки | 0,1 с |

На RED OS 8 и Ubuntu (ext4, pgbench 40 TPS) пауза была 1–3 с.

Рекомендации для нагруженных систем: запускать перенос в часы наименьшей нагрузки и
уменьшать COW-файл (`--cow-mb 256…1024`), если объём изменений за время переноса это
позволяет. Объём изменений можно оценить заранее: время загрузки × скорость записи на диск.

## Насколько согласованы данные

Снапшот **crash-consistent**: это то же состояние, что после внезапного отключения питания
в момент снапшота. Журналируемые ФС (ext4, xfs) и СУБД с журналом (PostgreSQL WAL,
InnoDB redo) при первой загрузке новой ВМ восстанавливаются сами.

Проверено на PostgreSQL под нагрузкой pgbench: после загрузки новой ВМ PostgreSQL догоняет
WAL, последняя запись в таблице совпадает с моментом снапшота, `amcheck` по индексам
чистый, инвариант pgbench (суммы балансов) сходится.

Если нужна согласованность на уровне приложения, приложение нужно ненадолго приостановить
непосредственно перед запуском агента.

## Что агент меняет в системе

| Что | Где | Когда |
|---|---|---|
| файлы агента | `/opt/disk2glance/`, ссылки `/usr/local/sbin/disk2glance`, `/usr/sbin/disk2glance` (и так же `disk2s3`) | при установке |
| правило SELinux (если SELinux включён) | `semanage fcontext`: `/opt/disk2glance/modules(/.*)?` → `modules_object_t` | при установке; удаляется при `--uninstall` |
| конфигурация | `/etc/disk2glance/openrc` (600), `props.json`, `disk2glance.conf` | при установке (из шаблонов, если файлов нет) или вручную |
| модуль ядра `dattobd` | в памяти ядра | только пока работает агент |
| COW-файлы `.datto_d2g` | в корне каждой снапшотируемой ФС (раздела или LV) | только пока работает агент |
| опция `discard` у ФС, `fstrim.timer` | ФС с `discard` перемонтируются `nodiscard`, таймер приостанавливается | только пока существуют снапшоты; потом возвращается как было |
| юнит `disk2glance-cowclean.service` | `/etc/systemd/system/` и ссылка в `multi-user.target.wants/` | несколько миллисекунд вокруг снапшота; остаётся только в копии |
| служебные файлы | `/run/disk2glance/` (lock, pid, md5, progress) | во время работы |

Пакеты из репозиториев **не ставятся**, компилятор **не нужен**, автозагрузка и
systemd-юниты **не меняются**. `install.sh --uninstall` удаляет всё перечисленное.

## Нагрузка на исходную ВМ во время переноса

- **Чтение:** весь диск читается последовательно один раз.
- **Запись:** каждая первая запись в блок после снапшота превращается в чтение старого
  блока, запись его в COW-файл и запись нового блока. На медленных дисках с лимитом
  IOPS (например ceph-hdd) задержки записи заметно растут.
- **Один поток ядра:** dattobd обслуживает чтение снапшота и COW одним потоком, поэтому
  интенсивное чтение снапшота замедляет запись на живую ФС.
- **Сеть:** один HTTP-поток в Glance. В VK Cloud это около 90 МиБ/с; две исходные ВМ, переносимые одновременно,
  дали 92 и 64 МиБ/с.

Замеры (20 ГБ, ceph-hdd, pgbench 40 TPS): снапшот готов за ~2 с, загрузка заняла 222 с (3,7 мин),
TPS pgbench не изменились, рост COW составил около 1 МБ/с.
