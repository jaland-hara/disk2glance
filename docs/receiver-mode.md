# Перенос на приёмник (экспериментальный режим, этап 1)

Термины (исходная ВМ, новая ВМ, бандл) объяснены в [README](../README.md#термины).

В этом режиме диск исходной ВМ уходит не в Glance и не в S3, а **сразу в том Cinder** целевого
облака. Том подключён к ВМ-приёмнику, на которой работает сервер `d2g`. Части диска идут по HTTPS
с проверкой сертификатов в обе стороны (mTLS) в несколько потоков. Приёмник записывает каждую
часть в том по её смещению и ведёт журнал «часть → MD5». Журнал даёт докачку после обрыва и
**дельты**: следующий проход с новым снапшотом отправляет только изменившиеся части.

На этапе 1 оркестратор и приёмник работают на одной ВМ и управляются командой `d2g`
(веб-интерфейса пока нет).

## Компоненты

| Компонент | Где | Что делает | Какие секреты у него есть |
|---|---|---|---|
| `d2g` (`server/d2g.py`) | ВМ в целевом облаке | свой CA, регистрация агентов, тома (создать, подключить к себе, отключить), приём частей, сборка ВМ из тома | учётка облака `/etc/d2g/openrc` (600), ключ CA |
| `disk2rx` (`disk2rx.sh`) | исходная ВМ | снапшоты dattobd (как `disk2glance`), разбиение диска на части, отправка | только свой клиентский сертификат |

Учётные данные облака на исходную ВМ не попадают. Агент может только писать в свой том через
приёмник.

## Доверие и шифрование

1. `d2g init` создаёт CA (EC P-256) и сертификат сервера на постоянное имя (например,
   `rx01.d2g`) и все его адреса: серый IP и FIP.
2. `d2g agent add NAME` выдаёт одноразовый токен (1 час) и готовую команду для исходной ВМ. В
   команде есть отпечаток ключа сервера (`--pin`).
3. `disk2rx --enroll` скачивает CA по соединению с проверкой отпечатка, создаёт ключ на исходной
   ВМ (ключ её не покидает) и отправляет запрос на сертификат с токеном и описанием системы:
   ОС, ядро, размер диска, есть ли модуль, свойства образа.
4. Дальше все запросы идут с клиентским сертификатом. Приёмник пускает агента только к его
   заданию. `d2g agent revoke` сразу закрывает агенту доступ.
5. Имя в TLS не зависит от пути: агент подключается к нужному адресу (`--connect`) с именем
   сервера (`curl --connect-to`), поэтому серый канал и FIP проверяются одинаково.

## Пути до приёмника

- **Серый IP** (Direct Connect из ЦОДа или источник в той же сети): `--connect 10.20.20.8`.
- **FIP приёмника** (источник за интернетом): `--connect <FIP>`. Исходящий трафик источника идёт
  через SNAT роутера, а входящий на приёмник приходит на его FIP.

Порт 443 в группе безопасности приёмника стоит открывать только для подсетей ЦОДа и адресов
источников (на стенде: `10.20.20.0/24` и SNAT-адрес роутера).

## Протокол

| Запрос | Что делает |
|---|---|
| `GET /v1/ca` | сертификат CA (без клиентского сертификата, для регистрации) |
| `POST /v1/enroll` | токен + запрос на сертификат + описание системы → сертификат |
| `GET /v1/agent/job` | текущее задание агента: id, размер диска, размер части |
| `POST /v1/jobs/<id>/start` | начало прохода, время снапшота |
| `GET /v1/jobs/<id>/parts` | журнал «часть → MD5» |
| `PUT /v1/jobs/<id>/parts/<n>` + `Content-MD5` | часть пишется в том потоком с подсчётом MD5 на лету; при несовпадении часть вычёркивается из журнала, ответ 400 |
| `PUT …/parts/<n>` + `X-D2G-Zero: 1` | нулевая часть без тела: на новом томе только отметка в журнале, иначе запись нулей |
| `POST /v1/jobs/<id>/complete` | MD5 всех частей; приёмник сверяет их с журналом и возвращает список недостающих (409) или `synced` |

Нагрузку ограничивают общий предел одновременных частей (по умолчанию 4 на vCPU) и предел на
одно задание (16). Лишние запросы получают `503`, агент ждёт и повторяет их, это не считается
ошибкой.

## Как перенести ВМ

На приёмнике (Ubuntu 24.04, один раз):

```bash
sudo server/install.sh --name rx01.d2g --ip <серый IP> --ip <FIP>
sudo vi /etc/d2g/openrc            # учётка облака (OS_AUTH_URL, OS_USERNAME, ...), права 600
sudo d2g agent add src1            # печатает команду с токеном для исходной ВМ
```

На исходной ВМ (бандл 0.6 с `disk2rx`):

```bash
sudo ./install.sh
sudo disk2rx --enroll --name src1 --server rx01.d2g --connect 10.20.20.8 --pin 'sha256//…' --token …
```

На приёмнике:

```bash
sudo d2g job new src1              # том нужного размера (ceph-ssd) -> подключить к себе -> задание
```

На исходной ВМ — первый проход, затем дельты (сколько угодно раз):

```bash
sudo disk2rx --threads 8
```

Сборка ВМ на приёмнике:

```bash
sudo d2g job finish <job> --flavor STD3-2-4 --network dmz01 --sg default --sg ssh --key mykey
sudo d2g job list
```

`finish` отключает том, делает его загрузочным, ставит свойства образа (из `props.json`
исходной ВМ или из `/etc/os-release`) и создаёт ВМ с загрузкой с тома в той же зоне.

## Что дальше

- **COW-файл dattobd в дельтах.** Он создаётся заново при каждом снапшоте (10 % ФС) и даёт
  заметную часть каждой дельты. Его экстенты можно отправлять как нули.
- **Дельта читает весь диск.** Это быстро на ceph-ssd, но на медленных дисках (как 14 МиБ/с в
  Яндексе) будет долго. Решение — трекинг изменённых блоков (CBT) в dattobd (incremental mode).
- **Приёмник упирается в CPU.** Больше vCPU, процесс на ядро вместо потоков, позже Go.
- **Общий код снапшотов** в `disk2glance`, `disk2s3`, `disk2rx` вынести в одну библиотеку.
- **Этап 2:** оркестратор как сервис (установщик из GitHub, приёмники создаются им через
  cloud-init, SNI-проброс через один FIP), затем веб-интерфейс.
