# Приёмник d2g: протокол, устройство, замеры

Как развернуть оркестратор и приёмники и перенести ВМ — в [orchestrator.md](orchestrator.md). Здесь
описано, как агент `disk2rx` и приёмник передают диск, и что показали замеры.

Диск исходной ВМ уходит **сразу в том Cinder**, подключённый к приёмнику. Части диска идут по
HTTPS с проверкой сертификатов в обе стороны (mTLS) в несколько потоков. Приёмник записывает
каждую часть в том по её смещению и ведёт журнал: для каждой части — MD5 её 16 блоков. Журнал даёт
докачку после обрыва и **дельты**: следующий проход с новым снапшотом отправляет только
изменившиеся блоки.

Управление (регистрация, задание, команды, отчёты) идёт к оркестратору, данные — к приёмнику.

## Протокол

Оркестратор (`ctl.<id>.d2g`): `GET /v1/ca`, `POST /v1/enroll` (токен + запрос на сертификат +
описание системы), `GET /v1/agent/job` (задание и адреса приёмника), `GET /v1/agent/command`
(`sync`, `uninstall`), `POST /v1/agent/report`; приёмники — `POST /v1/rx/join`, `POST /v1/rx/heartbeat`
(раз в 5 с: устройства, задания, прогресс → в ответ список заданий, которые приёмник обслуживает).

Приёмник (`rxN.<id>.d2g`):


| Запрос | Что делает |
|---|---|
| `GET /v1/ping` | проверка пути (агент выбирает первый ответивший адрес приёмника) |
| `POST /v1/jobs/<id>/start` | начало прохода, время снапшота |
| `GET /v1/jobs/<id>/parts` | журнал: для каждой части список MD5 её блоков `md5,md5,…` |
| `PUT /v1/jobs/<id>/parts/<n>` | `X-D2G-Blocks: i:md5,…` — тело состоит из этих блоков подряд; `X-D2G-Zero-Blocks: i,…` — нулевые блоки без данных. Блоки пишутся в том потоком (`O_DIRECT`) с подсчётом MD5 на лету; при несовпадении часть вычёркивается из журнала, ответ 400. Часть, которой нет в журнале, должна прийти целиком (409 иначе) |
| `POST /v1/jobs/<id>/complete` | для каждой части MD5 списка MD5 её блоков; приёмник сверяет с журналом и возвращает список недостающих (409) или `synced` |

**Части и блоки.** Часть — 64 МиБ (до 10 000 частей не ограничено, просто удобная единица
работы), блок — 1/16 части (4 МиБ). Агент хэширует блоки каждой части (`split --filter md5sum`)
и сравнивает с журналом. Отправляются только отличающиеся блоки, нулевые идут отметкой без данных.
На новом томе (он читается нулями) нулевые блоки части, которой ещё нет в журнале, не пишутся.

**COW-файлы dattobd.** Файл `.datto_d2g` создаётся заново при каждом снапшоте (10 % ФС) и попадает
в копию (там его удаляет служебный юнит при первой загрузке). Его содержимое не нужно, поэтому
агент берёт его экстенты (`filefrag`), переводит их в смещения на диске и отдаёт эти места
нулями: на проводе они ничего не стоят и не появляются в каждой дельте.

Сервер запускает по процессу-обработчику на ядро (TLS, MD5 и копирование в одном процессе
Python упираются в GIL). Общий предел одновременных частей (по умолчанию 4 на vCPU) общий для
всех процессов, предел на задание (16) — на процесс. Лишние запросы получают `503`, агент ждёт
секунду и повторяет, это не считается ошибкой.

Запись идёт в обход страничного кэша (`O_DIRECT`). Через кэш десятки параллельных частей
кончались штормом сброса: 650 МБ/с первые 20 с, потом 40–60 МБ/с при iowait 99 %.

## Приёмник не должен загружаться с тома задания

Том задания — побайтовая копия диска источника. Если источник сделан из того же облачного образа,
что и приёмник, у их ФС одинаковые UUID и метки (`cloudimg-rootfs`, `BOOT`, `UEFI`). При
перезагрузке приёмника с подключёнными томами (так было после смены флейвора) GRUB нашёл `/boot`
на томе задания, и приёмник **загрузил копию источника** (корень на `/dev/vdc1`, machine-id
источника). Копия поработала как ОС — тома заданий испорчены.

Поэтому:

- `server/unique-boot.sh` (вызывается установщиком) даёт корню, `/boot` и EFI приёмника новые
  UUID и метки (`d2g-root`, `d2g-boot`, `D2GEFI`), пишет `fstab` по UUID, переустанавливает GRUB и
  initramfs. Проверено: перезагрузка с четырьмя подключёнными копиями того же образа — приёмник
  поднимается со своего диска.
- `unique-boot.sh` запускается и на ВМ оркестратора, если на ней работает приёмник `rx0`.
- Приёмник (`d2g rx-serve`) не стартует, если корень оказался на томе какого-либо задания.

## Замеры (VK Cloud, 16.10.2026)

Приёмник `d2g-rx01` (этап 1, приёмник отдельно, управление командой `d2g` на нём же): PA2, системный диск ceph-ssd. Источники: STD3-2-4 (`src1`, `src2`, с
PostgreSQL + pgbench 40 транзакций/с и метками времени) и STD3-4-4 (`src3`, `src4`, без нагрузки),
Ubuntu 24.04, диски 20 ГБ ceph-ssd с 5–11 ГБ несжимаемых данных. Части по 64 МиБ, по 8 потоков
на источник. `src1`, `src3` — по серому IP, `src2`, `src4` — через FIP.

**Этап 1 (части целиком, потоки в одном процессе, приёмник 4 vCPU)**

| Тест | Результат |
|---|---|
| `src1` + `src2` одновременно | 20 ГиБ за 77 и 80 с, вместе ~520 МиБ/с; CPU приёмника ~99 % |
| Дельта `src1` / `src2` (+3 ГиБ данных) | 43 и 101 часть из 320, 2,7 и 6,3 ГиБ |

**Блоки, COW-файл нулями, `O_DIRECT`, процесс на ядро, приёмник 8 vCPU (STD3-8-8)**

| Тест | Результат |
|---|---|
| Первый проход, **4 источника одновременно** | 51, 56, 74 и 85 с; 10,2–16,0 ГиБ на проводе каждый (COW-файл 2 ГиБ и нулевые блоки не передаются); **запись на приёмнике ~1 ГБ/с**, CPU ~80 %, 0 повторов, 0 ответов 503 |
| То же без `O_DIRECT` (через страничный кэш) | 334–480 с: после 20 с запись падает до 40–60 МБ/с при iowait 99 % |
| Дельта `src1` (только pgbench) | **208–332 МиБ** на проводе (было 2,7 ГиБ), проход 63–64 с — почти всё время чтение и хэширование всего диска на 2 vCPU |
| Дельта `src3`/`src4` (без нагрузки) | 108 МиБ, проход 42–44 с, чтение диска 465–487 МиБ/с |
| Перезагрузка приёмника с 4 подключёнными томами (до `unique-boot.sh`) | загрузилась копия источника — см. раздел выше |
| То же после `unique-boot.sh` | приёмник на своём диске, журналы на месте, следующая дельта прошла |
| Проверка клонов `src1` (серый IP, pgbench) и `src4` (FIP) | PostgreSQL восстановился, последняя метка в файле и в базе = момент снапшота, `amcheck` чистый, инвариант pgbench сходится, MD5 файлов с данными совпадают с источником, COW-файлы удалены |
| Прерывание агента и SIGKILL (этап 1) | снапшоты убраны (после SIGKILL — следующим запуском), `fstrim.timer` возвращён, докачка принимает только недостающее |
| `d2g job finish` | ВМ `ACTIVE` через ~20 с |

## Что дальше

- **Дельта читает весь диск.** Это быстро на ceph-ssd, но на медленных дисках (как 14 МиБ/с в
  Яндексе) будет долго. Решение — трекинг изменённых блоков (CBT) в dattobd (incremental mode).
- **Хэширование на источнике.** На 2 vCPU агент упирается в CPU (`dd`, `md5sum`, `curl`). Можно
  ограничивать его (`nice`, меньше потоков), чтобы не мешать приложениям.
- **Общий код снапшотов** в `disk2glance`, `disk2s3`, `disk2rx` вынести в одну библиотеку.
- Замеры этапа 2 (оркестратор, `rx0`, приёмники через cloud-init) — в [orchestrator.md](orchestrator.md#проверено-vk-cloud-16102026).
