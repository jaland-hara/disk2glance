# Приёмник и протокол передачи

Как агент `disk2rx` и приёмник передают диск при переносе через оркестратор (подробности
протокола; обзор со схемами — в [agent.md](agent.md)). Как развернуть
оркестратор и перенести ВМ — в [guide.md](guide.md) и
[orchestrator.md](orchestrator.md). Термины — в [README](../README.md#термины), оглавление документации — в [docs/README.md](README.md).

Каждый диск исходной ВМ передаётся **сразу в свой том Cinder**, подключённый к приёмнику. Части диска
передаются по HTTPS с проверкой сертификатов обеими сторонами (mTLS) в несколько потоков.
Приёмник записывает каждую часть в том по её смещению и ведёт журнал: для каждой части — MD5 её
16 блоков. Журнал позволяет продолжить передачу после обрыва и выполнять **дельты**: следующий
проход с новым снапшотом отправляет только изменившиеся блоки.

Запросы управления (регистрация, задание, команды, отчёты) направляются оркестратору, данные —
приёмнику.

## Протокол

Оркестратор (`ctl.<id>.d2g`): `GET /v1/ca`, `POST /v1/enroll` (токен + запрос на сертификат +
описание системы и список дисков), `POST /v1/agent/inventory` (список дисков: при запуске
службы агента и раз в час), `GET /v1/agent/job` (задание, его диски и адреса приёмника),
`GET /v1/agent/command` (`sync`, `uninstall`), `POST /v1/agent/report`; приёмники — `POST /v1/rx/join`, `POST /v1/rx/heartbeat`
(раз в 5 с: устройства, задания, прогресс → в ответ список заданий, которые приёмник обслуживает).

Приёмник (`rxN.<id>.d2g`):


| Запрос | Что делает |
|---|---|
| `GET /v1/ping` | проверка пути (агент выбирает первый ответивший адрес приёмника) |
| `POST /v1/jobs/<id>/start` | начало прохода, время снапшота |
| `GET /v1/jobs/<id>/parts` | журнал: для каждой части список MD5 её блоков `md5,md5,…` |
| `PUT /v1/jobs/<id>/parts/<n>` | `X-D2G-Blocks: i:md5,…` — тело состоит из этих блоков подряд; `X-D2G-Zero-Blocks: i,…` — нулевые блоки без данных. Блоки записываются в том потоком (`O_DIRECT`) с вычислением MD5 при записи; при несовпадении часть удаляется из журнала, ответ 400. Часть, которой нет в журнале, должна быть передана целиком (иначе ответ 409) |
| `POST /v1/jobs/<id>/complete` | для каждой части MD5 списка MD5 её блоков; приёмник сверяет с журналом и возвращает список недостающих (409) или `synced` |

**Части и блоки.** Часть — 64 МиБ (число частей не ограничено; часть — единица работы), блок —
1/16 части (4 МиБ). Агент хеширует блоки каждой части (`split --filter md5sum`)
и сравнивает с журналом. Отправляются только отличающиеся блоки, нулевые передаются отметкой без
данных. На новом томе (он читается нулями) нулевые блоки части, которой ещё нет в журнале, не
записываются.

**COW-файлы dattobd.** Файл `.datto_d2g` создаётся заново при каждом снапшоте (10 % ФС) и попадает
в копию (там его удаляет служебный юнит при первой загрузке). Его содержимое не нужно, поэтому
агент получает его экстенты (`filefrag`), переводит их в смещения на диске и передаёт эти
участки как нулевые: они не занимают канал и не попадают в каждую дельту.

Сервер запускает по процессу-обработчику на ядро (TLS, MD5 и копирование в одном процессе
Python ограничены GIL). Предел одновременных частей (по умолчанию 4 на vCPU, вычисляется при
каждом запуске) общий для всех процессов, предел на задание (16) — на процесс. Лишние запросы получают `503`, агент ждёт
секунду и повторяет, это не считается ошибкой.

Запись выполняется в обход страничного кэша (`O_DIRECT`). При записи через кэш десятки
параллельных частей вызывали массовый сброс кэша на диск: 650 МБ/с первые 20 с, затем
40–60 МБ/с при iowait 99 %.

## Несколько дисков

У задания столько томов, сколько дисков в нём. Для приёмника каждый том — отдельное «задание»
со своим идентификатором, журналом и запросами `/v1/jobs/<id>/…`: том загрузочного диска имеет
идентификатор задания (`j1a2b3c4d`), остальные — `j1a2b3c4d-1`, `j1a2b3c4d-2` и т. д. В ответе
`GET /v1/agent/job` — список `disks`: идентификатор, имя устройства и серийный номер диска на
исходной ВМ, размер.

Агент снимает один набор снапшотов, вызывает `start` для всех томов, затем передаёт и сверяет
(`complete`) их по очереди. Оркестратор собирает состояние задания из состояний томов: задание
«Синхронизировано», только если все тома сверены с одним и тем же временем снапшота.
Ограничение «томов на приёмник» считает тома, а не задания: задание из пяти дисков занимает пять
мест.

## Приёмник не должен загружаться с тома задания

Том задания — побайтовая копия диска источника. Если источник сделан из того же облачного образа,
что и приёмник, у их ФС одинаковые UUID и метки (`cloudimg-rootfs`, `BOOT`, `UEFI`). При
перезагрузке приёмника с подключёнными томами (так было после смены флейвора) GRUB нашёл `/boot`
на томе задания, и приёмник **загрузил копию источника** (корень на `/dev/vdc1`, machine-id
источника). Копия работала как ОС, и тома заданий были повреждены.

Поэтому:

- `server/unique-boot.sh` (вызывается установщиком) даёт корню, `/boot` и EFI приёмника новые
  UUID и метки (`d2g-root`, `d2g-boot`, `D2GEFI`), записывает `fstab` по UUID, переустанавливает GRUB и
  initramfs. Проверено: при перезагрузке с четырьмя подключёнными копиями того же образа приёмник
  загружается со своего диска.
- `unique-boot.sh` запускается и на ВМ оркестратора, если на ней работает приёмник `rx0`.
- Приёмник (`d2g rx-serve`) не запускается, если корень оказался на томе какого-либо задания.

## Приёмник не активирует LVM томов заданий

Тома заданий могут содержать PV групп томов источника. После записи в том udev перечитывает
диск, и LVM приёмника мог бы активировать группу: активный LV занял бы том (запись отклоняется
проверкой `holders`, отключение тома зависает), а группы с одинаковыми именами с разных
источников конфликтовали бы. Поэтому установщик сервера (`install.sh`) на приёмниках и на ВМ
оркестратора с `rx0` дописывает в `/etc/lvm/lvmlocal.conf` фильтр: LVM видит только диск, с
которого загружена ВМ, и автоматическая активация выключена. Проверено: после передачи томов
с LVM `dmsetup ls` на приёмнике пуст, `pvs` томов заданий не видит.

## Планы

- **Дельта читает весь диск.** На ceph-ssd это быстро, но на медленных дисках (например,
  14 МиБ/с в Яндексе) займёт много времени. Решение — отслеживание изменённых блоков (CBT) в
  dattobd (incremental mode).
- **Хеширование на источнике.** На 2 vCPU производительность агента ограничена CPU (`dd`,
  `md5sum`, `curl`). Агента можно ограничивать (`nice`, меньше потоков), чтобы он не мешал
  приложениям.

- **Общий код снапшотов** в `disk2glance`, `disk2s3`, `disk2rx` вынести в одну библиотеку.
- Замеры этапа 2 (оркестратор, `rx0`, приёмники через cloud-init) — в [orchestrator.md](test-reports.md#оркестратор-и-приёмники-16102026).
