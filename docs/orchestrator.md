# Инфраструктура d2g: оркестратор и приёмники (экспериментально)

Термины (исходная ВМ, новая ВМ, бандл) объяснены в [README](../README.md#термины). Протокол
передачи, устройство приёмника и замеры описаны в [receiver-mode.md](receiver-mode.md).

В этой поставке диск исходной ВМ переносится **сразу в том Cinder** целевого проекта, без Glance
и S3. Можно повторять проходы с новым снапшотом: каждый следующий проход (дельта) передаёт только
изменившиеся блоки. Когда пора переключаться, оркестратор собирает ВМ из тома.

## Состав

| Компонент | Где | Что делает | Какие секреты у него есть |
|---|---|---|---|
| **Оркестратор** (`d2g`, сервис `d2g-orch`) | одна ВМ в целевом проекте клиента | свой CA, регистрация агентов и приёмников, тома (создать, подключить, отключить), создание приёмников, сборка ВМ из тома, расписание дельт | учётка облака `/etc/d2g/openrc` (600), ключ CA |
| **Приёмник rx0** (`d2g-rx`) | на ВМ оркестратора (по умолчанию) | принимает части от агентов и пишет их в подключённые тома | только свой сертификат |
| Приёмники rx1… | отдельные ВМ, их создаёт оркестратор (cloud-init) | то же, для масштабирования и других зон | только свой сертификат |
| nginx (stream) | ВМ оркестратора, порт 443 | разбирает соединения по имени в TLS (SNI) без расшифровки: `ctl.<id>.d2g` → API, `rxN.<id>.d2g` → приёмник | — |
| **Агент** `disk2rx` (сервис `disk2rx-agent`) | исходная ВМ | снапшоты dattobd, отправка частей, выполнение команд оркестратора | только свой клиентский сертификат |

Учётные данные облака есть только у оркестратора. Агент может только писать в свой том через
приёмник. Приёмник не знает учётку облака.

```
  исходные ВМ (ЦОД, другие облака)                    целевой проект VK Cloud
  ┌──────────────┐  443 (mTLS)   ┌──────────────────────────────────────────────┐
  │ disk2rx      │──────────────▶│ ВМ оркестратора, FIP                          │
  │ (агент)      │ серый канал   │  nginx :443 ─ SNI ─▶ d2g-orch (API, CA, облако)│
  └──────────────┘ или интернет  │                └──▶ d2g-rx rx0 ─▶ тома заданий│
                                 │                └──▶ rx1, rx2… (отдельные ВМ)  │
                                 └──────────────────────────────────────────────┘
```

## Доверие и шифрование

1. `d2g setup` создаёт CA (EC P-256) и сертификат оркестратора на имя `ctl.<id>.d2g`.
2. `d2g agent add NAME` выдаёт одноразовый токен (1 час) и команду установки, в которой есть
   отпечаток ключа оркестратора. Скрипт установки скачивается по TLS с проверкой этого отпечатка
   (`curl --pinnedpubkey`). Он берёт бандл агента у оркестратора и регистрирует агента.
3. Ключ агента создаётся на исходной ВМ и её не покидает. Оркестратор подписывает запрос на
   сертификат с именем агента. Вместе с запросом агент присылает описание системы: ОС, ядро, диск,
   есть ли модуль dattobd, свойства образа.
4. Приёмник получает сертификат так же, по одноразовому токену из cloud-init (у `rx0` его сразу
   выпускает оркестратор). В сертификате приёмника его имя `rxN.<id>.d2g`.
5. Все соединения — TLS с проверкой сертификатов в обе стороны. Приёмник пускает агента только к
   тому заданию, где совпадают имя и серийный номер сертификата агента. `d2g agent revoke` закрывает
   доступ на всех приёмниках в течение 5 с.
6. Агент подключается к нужному адресу с именем сервера (`curl --connect-to`), поэтому серый
   канал, FIP и проброс через оркестратор проверяются одинаково, и DNS не нужен.

### Копия не может выдать себя за источник

Новая ВМ — копия диска источника, поэтому в ней есть сертификат агента и служба `disk2rx-agent`.
Без защиты копия опрашивала бы оркестратор под именем источника и могла бы выполнить его команду.
Поэтому:

- служебный юнит, который на копии при первой загрузке удаляет COW-файлы dattobd, запускается
  раньше агента и удаляет его идентичность (`d2g.env`, ключ, сертификат) и автозапуск;
- при регистрации агент запоминает UUID ВМ (`/sys/class/dmi/id/product_uuid`, в OpenStack это ID
  инстанса). Если при запуске UUID другой, агент удаляет идентичность и выключается.

## Пути до приёмника

Оркестратор отдаёт агенту адреса приёмника по порядку, агент берёт первый, который ответил:

| Путь | Когда |
|---|---|
| `rx-grey`: серый IP приёмника | источник в ЦОДе за Direct Connect или в той же сети |
| `rx-fip`: FIP приёмника | у отдельного приёмника есть свой FIP из пула (`d2g setup --fip-pool`) |
| `ctl`: публичный адрес оркестратора, дальше SNI | источник за интернетом, отдельного FIP нет; для `rx0` это основной путь |
| `ctl-grey`: серый адрес оркестратора, дальше SNI | источник в ЦОДе, но до приёмника напрямую не достать |

Путь можно закрепить за агентом: `d2g agent add NAME --path ctl`.

nginx передаёт приёмникам и API реальный адрес источника (PROXY protocol), поэтому в
`d2g agent list` виден адрес, с которого пришёл агент.

## Установка оркестратора

ВМ в целевом проекте: Ubuntu 24.04. Если на ней же работает приёмник `rx0`, рекомендуется 4–8 vCPU
(на 2 vCPU два параллельных переноса занимают CPU полностью). Системный диск ceph-ssd. Нужен FIP,
если источники за интернетом.

Группа безопасности ВМ оркестратора: 443 от источников (подсети ЦОДа, адреса исходных ВМ или их
SNAT) и от сети приёмников. 22 — для администратора.

```bash
# бандл d2g-server-<версия>.tar.gz из Releases
tar xzf d2g-server-0.6.0.tar.gz && cd d2g-server-0.6.0
sudo install -d /etc/d2g && sudo install -m 600 openrc /etc/d2g/openrc   # учётка проекта (сервисная)
sudo ./install.sh --role orch --public-ip <FIP> --allow 10.0.0.0/8 --allow <адрес источника>/32
sudo d2g status
```

`install.sh --role orch`:
- ставит nginx с модулем stream;
- кладёт код в `/opt/d2g`, а бандлы для раздачи (агент и сервер) в `/opt/d2g/pkg`;
- запускает `d2g setup`: CA, сертификат, группа безопасности `d2g-receivers`, локальный приёмник
  `rx0`, конфиг nginx;
- запускает `unique-boot.sh`, потому что к этой ВМ будут подключаться тома с копиями дисков (см.
  [receiver-mode.md](receiver-mode.md#приёмник-не-должен-загружаться-с-тома-задания));
- включает `d2g-orch` и `d2g-rx`.

Параметры `d2g setup`, их можно менять повторным запуском:

| Параметр | Что это |
|---|---|
| `--public-ip IP` | публичный адрес (FIP) оркестратора для агентов из интернета |
| `--allow CIDR` | кому открыт 443 на отдельных приёмниках (`d2g-receivers`) |
| `--fip-pool ID` | плавающие IP, которые можно отдавать отдельным приёмникам |
| `--rx-flavor`, `--rx-image`, `--rx-volume-type`, `--rx-key`, `--rx-sg` | ВМ отдельных приёмников (по умолчанию STD3-4-4, образ ВМ оркестратора, ceph-ssd) |
| `--no-local-receiver` | не поднимать `rx0`, только отдельные приёмники |

## Перенос

```bash
# 1. агент: команда с токеном, выполнить на исходной ВМ от root
sudo d2g agent add web01
#   curl -fsS -k --pinnedpubkey 'sha256//…' --connect-to ctl.690c2f.d2g:443:<IP>:443 \
#     https://ctl.690c2f.d2g/install.sh | sudo sh -s -- <IP> <токен> web01

# 2. задание: том по размеру диска -> подключить к приёмнику -> первый проход стартует сам
sudo d2g job new web01 [--every 3600]      # --every: дельта раз в час
sudo d2g job list

# 3. дельты по команде или по расписанию
sudo d2g job sync <job>
sudo d2g job sync <job> --every 1800

# 4. переключение: остановить приложение на источнике (по желанию), последняя дельта, сборка ВМ
sudo d2g job sync <job>
sudo d2g job finish <job> --flavor STD3-4-8 --network <сеть> --sg default --key <ключ> [--name web01]

# 5. убрать агента с источника
sudo d2g agent uninstall web01
```

`job finish` дожидается, пока приёмник отпустит том, отключает том, делает его загрузочным, ставит
свойства образа (из `props.json` источника или из `/etc/os-release`) и создаёт ВМ с загрузкой с
тома в той же зоне. `job delete` отпускает и удаляет том.

Если у приёмника в нужной зоне нет свободного места под тома (по умолчанию 20 томов на приёмник),
`job new` сам создаёт новый приёмник. Его можно создать и заранее:

```bash
sudo d2g receiver add [--az PA2] [--flavor STD3-8-8] [--fip <id>|auto]
sudo d2g receiver list
sudo d2g receiver delete rx1
```

Новый приёмник поднимается примерно за 1,5 минуты: том из образа, ВМ, cloud-init скачивает бандл
у оркестратора, `unique-boot.sh`, регистрация, первый отчёт.

## Проверено (VK Cloud, 16.10.2026)

Оркестратор `d2g-ctl01`: STD3-2-4, PA2, FIP. Источники: Ubuntu 24.04, 20 ГБ ceph-ssd; `src1` с
PostgreSQL + pgbench, `src4` с 10 ГБ данных.

| Проверка | Результат |
|---|---|
| Установка оркестратора из бандла | nginx (SNI), API, CA, `rx0`, `unique-boot.sh` — одной командой |
| `d2g receiver add` | приёмник `rx1` поднят за 1 мин 30 с, без ручных действий |
| Установка агента одной командой (серый адрес и FIP оркестратора) | агент скачан у оркестратора, зарегистрирован, `disk2rx-agent` запущен; оркестратор видит настоящий адрес источника |
| `d2g job new` для двух агентов | тома созданы и подключены, первый проход стартовал сам; `src1` выбрал серый IP приёмника, `src4` — SNI через оркестратор |
| Первый проход через отдельный `rx1` | 69 и 56 с |
| Первый проход через `rx0` на ВМ оркестратора (2 vCPU) | 91 и 84 с, ответы «занят» (503): 65–75 — CPU оркестратора загружен полностью |
| Дельта по команде `d2g job sync` | `src1`: 164 МиБ, 60 с; `src4` (+1 ГиБ данных): 1,1 ГиБ, 43 с |
| `d2g job finish` | ВМ `ACTIVE` за ~20 с; клон `src1` — PostgreSQL восстановился, метка = момент снапшота, `amcheck` чистый; клон `src4` — MD5 данных совпадают, включая файл из дельты |
| Защита от копии | на клоне `src4` агент выключен, идентичность удалена; оркестратор видит только настоящий источник |
| `d2g job delete`, `d2g receiver delete` | том удалён; приёмник удалён, nginx перенастроен |

### Из другой площадки: VK Cloud KZ → VK Cloud RU (17.10.2026)

Источник `d2g-kz-src1` в KZ: Standard-4-8, Ubuntu 24.04, диск 100 ГБ ceph-ssd, PostgreSQL + pgbench и
40 ГБ несжимаемых данных. В интернет выходит через роутер (SNAT), FIP у источника нет (SSH через
отдельный jump с FIP). Приёмник — `rx0` на ВМ оркестратора в RU (STD3-4-8). Агент сам выбрал путь
`ctl`: серый адрес приёмника из KZ недоступен.

| Проверка | Результат |
|---|---|
| Первый проход, 8 потоков | 1668 с (28 мин): из 100 ГБ диска по проводу 35,3 ГиБ (COW-файл 10 ГБ и пустые блоки не передаются), 21 МиБ/с, 0 повторов; приёмник загружен на 21 % |
| Дельта +5 ГБ: 8 / 24 потока | 16 / 12 МиБ/с — больше потоков не помогает |
| Канал без нашего протокола (поток по SSH на ВМ оркестратора) | через SNAT роутера KZ: 1 поток 12–15 МиБ/с, 8 потоков вместе 6 МиБ/с; **через FIP (jump-хост): 31 МиБ/с** |
| Последняя дельта (pgbench) | 392 МиБ, 236 с — почти всё время чтение диска 100 ГБ (433 МиБ/с) |
| ВМ в RU из тома (`job finish`) | загрузилась; PostgreSQL восстановился, последняя метка в файле и в базе = момент снапшота, `amcheck` чистый, инвариант pgbench сходится; MD5 всех 5 файлов с данными (40 ГБ) совпадают с источником; агент на копии выключен |

Вывод: из KZ упор в выход источника в интернет через роутер (сетевой узел), а не в приёмник или
протокол. Источник с собственным FIP выходит примерно вдвое быстрее. Если переносить много ВМ из
одной площадки, стоит выдавать источникам FIP на время переноса или планировать время по
скорости SNAT (~15–20 МиБ/с на источник; один источник на 100 ГБ с 35 ГБ данных — около 30 минут).
Дельта читает весь диск, поэтому на больших дисках её время определяет скорость чтения, а не канал.

Замечание: при первой загрузке ВМ `unattended-upgrades` обновил nginx и перезапустил его посреди
передачи. Передача через оркестратор пережила это за счёт повторов (7 повторов частей).
