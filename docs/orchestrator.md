# Инфраструктура d2g: оркестратор и приёмники (экспериментально)

Термины (исходная ВМ, новая ВМ, бандл) объяснены в [README](../README.md#термины). Протокол
передачи, устройство приёмника и замеры описаны в [receiver-mode.md](receiver-mode.md).

В этой поставке диск исходной ВМ переносится **сразу в том Cinder** целевого проекта, без Glance
и S3. Можно повторять проходы с новым снапшотом: каждый следующий проход (дельта) передаёт только
изменившиеся блоки. Когда пора переключаться, оркестратор собирает ВМ из тома.

## Состав

| Компонент | Где | Что делает | Какие секреты у него есть |
|---|---|---|---|
| **Оркестратор** (`d2g`, сервис `d2g-orch`) | одна ВМ в целевом проекте клиента | свой CA, регистрация агентов и приёмников, тома (создать, подключить, отключить), создание приёмников, сборка ВМ из тома, расписание дельт | учётка облака `/etc/d2g/openrc` (600), ключ CA |
| **Приёмник rx0** (`d2g-rx`) | на ВМ оркестратора (по умолчанию) | принимает части от агентов и пишет их в подключённые тома | только свой сертификат |
| Приёмники rx1… | отдельные ВМ, их создаёт оркестратор (cloud-init) | то же, для масштабирования и других зон | только свой сертификат |
| nginx (stream) | ВМ оркестратора, порт 443 | разбирает соединения по имени в TLS (SNI) без расшифровки: `ctl.<id>.d2g` → API, `rxN.<id>.d2g` → приёмник | — |
| **Агент** `disk2rx` (сервис `disk2rx-agent`) | исходная ВМ | снапшоты dattobd, отправка частей, выполнение команд оркестратора | только свой клиентский сертификат |

Учётные данные облака есть только у оркестратора. Агент может только писать в свой том через
приёмник. Приёмник не знает учётку облака.

```
  исходные ВМ (ЦОД, другие облака)                    целевой проект VK Cloud
  ┌──────────────┐  443 (mTLS)   ┌──────────────────────────────────────────────┐
  │ disk2rx      │──────────────▶│ ВМ оркестратора, FIP                          │
  │ (агент)      │ серый канал   │  nginx :443 ─ SNI ─▶ d2g-orch (API, CA, облако)│
  └──────────────┘ или интернет  │                └──▶ d2g-rx rx0 ─▶ тома заданий│
                                 │                └──▶ rx1, rx2… (отдельные ВМ)  │
                                 └──────────────────────────────────────────────┘
```

## Доверие и шифрование

1. `d2g setup` создаёт CA (EC P-256) и сертификат оркестратора на имя `ctl.<id>.d2g`.
2. `d2g agent add NAME` выдаёт одноразовый токен (1 час) и команду установки, в которой есть
   отпечаток ключа оркестратора. Скрипт установки скачивается по TLS с проверкой этого отпечатка
   (`curl --pinnedpubkey`). Он берёт бандл агента у оркестратора и регистрирует агента.
3. Ключ агента создаётся на исходной ВМ и её не покидает. Оркестратор подписывает запрос на
   сертификат с именем агента. Вместе с запросом агент присылает описание системы: ОС, ядро, диск,
   есть ли модуль dattobd, свойства образа.
4. Приёмник получает сертификат так же, по одноразовому токену из cloud-init (у `rx0` его сразу
   выпускает оркестратор). В сертификате приёмника его имя `rxN.<id>.d2g`.
5. Все соединения — TLS с проверкой сертификатов в обе стороны. Приёмник пускает агента только к
   тому заданию, где совпадают имя и серийный номер сертификата агента. `d2g agent revoke` закрывает
   доступ на всех приёмниках в течение 5 с.
6. Агент подключается к нужному адресу с именем сервера (`curl --connect-to`), поэтому серый
   канал, FIP и проброс через оркестратор проверяются одинаково, и DNS не нужен.

### Копия не может выдать себя за источник

Новая ВМ — копия диска источника, поэтому в ней есть сертификат агента и служба `disk2rx-agent`.
Без защиты копия опрашивала бы оркестратор под именем источника и могла бы выполнить его команду.
Поэтому:

- служебный юнит, который на копии при первой загрузке удаляет COW-файлы dattobd, запускается
  раньше агента и удаляет его идентичность (`d2g.env`, ключ, сертификат) и автозапуск;
- при регистрации агент запоминает UUID ВМ (`/sys/class/dmi/id/product_uuid`, в OpenStack это ID
  инстанса). Если при запуске UUID другой, агент удаляет идентичность и выключается.

## Пути до приёмника

Оркестратор отдаёт агенту адреса приёмника по порядку, агент берёт первый, который ответил:

| Путь | Когда |
|---|---|
| `rx-grey`: серый IP приёмника | источник в ЦОДе за Direct Connect или в той же сети |
| `rx-fip`: FIP приёмника | у отдельного приёмника есть свой FIP из пула (`d2g setup --fip-pool`) |
| `ctl`: публичный адрес оркестратора, дальше SNI | источник за интернетом, отдельного FIP нет; для `rx0` это основной путь |
| `ctl-grey`: серый адрес оркестратора, дальше SNI | источник в ЦОДе, но до приёмника напрямую не достать |

Путь можно закрепить за агентом: `d2g agent add NAME --path ctl`.

nginx передаёт приёмникам и API реальный адрес источника (PROXY protocol), поэтому в
`d2g agent list` виден адрес, с которого пришёл агент.

## Установка оркестратора

**ВМ:** Ubuntu 24.04 (или 22.04, Debian 12) в целевом проекте. Если на ней же работает приёмник
`rx0` (по умолчанию), рекомендуется 4–8 vCPU: на 2 vCPU два параллельных переноса занимают CPU
полностью. Системный диск ceph-ssd. FIP нужен, если источники или администраторы приходят из
интернета. Порт 22 — для администратора, 443 мастер может открыть сам. Чтобы у ВМ было по
очереди сетевой карты на vCPU, до создания ВМ поставьте на загрузочный том
`openstack volume set --image-property hw_vif_multiqueue_enabled=true <том>` (приёмники и
собираемые ВМ оркестратор создаёт так сам, см. [speed-tests.md](speed-tests.md#сеть-вм-multiqueue)).

**Учётка облака:** сервисная учётная запись проекта. Какие роли нужны — в
[service-accounts.md](service-accounts.md#учётная-запись-оркестратора-вариант-2).

### Одной командой и мастер в браузере

```bash
curl -fsSL https://github.com/jaland-hara/disk2glance/releases/latest/download/d2g-server-install.sh | sudo bash
```

Скрипт скачивает `d2g-server-<версия>.tar.gz` из Releases, сверяет SHA-256, ставит nginx и
оркестратор и запускает его в режиме первоначальной настройки. В конце он печатает:

```
  d2g orchestrator ctl.5ed4d7.d2g is waiting for its setup.
  Open    https://<FIP>/setup   (grey address: https://10.20.20.30/setup)
  Code    6476-a9c1-1226    (valid 1 hour, once; a new one: sudo d2g setup-code)
  Check the certificate in the browser: SHA-256 2F:F9:33:…:60:1E
```

Параметры (после `sudo bash -s --`): `--version 0.6.0` (по умолчанию последний релиз),
`--bundle FILE` (установка из скачанного архива, без интернета), `--public-ip IP`, `--ui-allow CIDR`
(сузить, откуда открывается мастер; по умолчанию — откуда угодно, но только с кодом).

В браузере откройте адрес, сверьте отпечаток сертификата, введите код. Шаги мастера:

| Шаг | Что задаётся |
|---|---|
| 1. Администратор | имя и пароль (от 12 символов); по желанию TOTP: QR-код для приложения, код проверяется сразу |
| 2. Облако | адрес Keystone, проект, сервисная учётка, домен (`service-users`), регион. «Проверить» делает настоящие пробы: видна ли эта ВМ, создаётся и удаляется том 1 ГБ и группа безопасности, видны ли FIP. Без пройденной проверки дальше можно идти только явно |
| 3. Размещение | зона, сеть, публичный адрес — подставлены из метаданных ВМ |
| 4. Приёмники | приёмник на этой ВМ (да/нет), тип томов, томов на приёмник, флейвор и ключ отдельных приёмников, FIP для них (только из свободных) |
| 5. Доступ | откуда открыт интерфейс (ваш адрес подставлен), откуда приходят исходные ВМ; по желанию — открыть 443 в группе безопасности `d2g-ctl` и подключить её к ВМ |
| 6. Применить | сводка → учётка в `/etc/d2g/openrc` (600), `d2g setup`, администратор, группа безопасности, `unique-boot.sh` и приёмник `rx0`, перезапуск в обычный режим |

После этого мастер закрывается (код больше не действует), открывается вход в интерфейс. Мастер
не даст сохранить список доступа без вашего текущего адреса.

### Вручную, без мастера

```bash
tar xzf d2g-server-0.6.0.tar.gz && cd d2g-server-0.6.0
sudo install -d /etc/d2g && sudo install -m 600 openrc /etc/d2g/openrc   # учётка проекта
sudo ./install.sh --role orch --public-ip <FIP> --allow 10.0.0.0/8 --ui-allow <адрес администратора>/32
sudo d2g admin add admin
sudo d2g status
```

Если `/etc/d2g/openrc` есть, `install.sh --role orch` сразу выполняет `d2g setup` с переданными
параметрами; если нет — запускает мастер. Повторный запуск `install.sh` обновляет код и
сохраняет настройки.

### Что делает установка

- ставит nginx с модулем stream;
- кладёт код в `/opt/d2g`, а бандлы для раздачи (агент и сервер) — в `/opt/d2g/pkg`;
- `d2g setup`: CA, сертификаты (агентский API по имени `ctl.<id>.d2g`, интерфейс по IP), группа
  безопасности `d2g-receivers`, локальный приёмник `rx0`, конфиг nginx;
- `unique-boot.sh`, потому что к этой ВМ будут подключаться тома с копиями дисков (см.
  [receiver-mode.md](receiver-mode.md#приёмник-не-должен-загружаться-с-тома-задания));
- службы `d2g-orch` и `d2g-rx`.

### Настройки после установки

Вкладка «Настройки» в интерфейсе: «Изменить доступ» (интерфейс и источники), «Изменить
приёмники» (флейвор, тип томов, томов на приёмник, пул FIP), «Учётка облака» (новая учётка
проверяется теми же пробами и сохраняется, только если все проверки прошли). Изменения
применяются сразу и пишутся в журнал.

Те же параметры в командной строке:

| Параметр `d2g setup` | Что это |
|---|---|
| `--public-ip IP` | публичный адрес (FIP) оркестратора для агентов из интернета |
| `--allow CIDR` | кому открыт 443 на отдельных приёмниках (`d2g-receivers`) |
| `--ui-allow CIDR` | откуда открывается веб-интерфейс |
| `--fip-pool ID` | плавающие IP, которые можно отдавать отдельным приёмникам |
| `--replace-lists` | `--allow`, `--ui-allow`, `--fip-pool` заменяют списки, а не дополняют |
| `--rx-flavor`, `--rx-image`, `--rx-volume-type`, `--rx-key`, `--rx-sg`, `--max-volumes` | отдельные приёмники (по умолчанию STD3-4-4, образ ВМ оркестратора, ceph-ssd, 20 томов) |
| `--no-local-receiver` | не поднимать `rx0`, только отдельные приёмники |
| `--ui-mtls on\|off` | требовать сертификат администратора в браузере |

## Перенос

```bash
# 1. агент: команда с токеном, выполнить на исходной ВМ от root
sudo d2g agent add web01
#   curl -fsS -k --pinnedpubkey 'sha256//…' --connect-to ctl.690c2f.d2g:443:<IP>:443 \
#     https://ctl.690c2f.d2g/install.sh | sudo sh -s -- <IP> <токен> web01

# 2. задание: том по размеру диска -> подключить к приёмнику -> первый проход стартует сам
sudo d2g job new web01 [--every 3600]      # --every: дельта раз в час
sudo d2g job list

# 3. дельты по команде или по расписанию
sudo d2g job sync <job>
sudo d2g job sync <job> --every 1800

# 4. переключение: остановить приложение на источнике (по желанию), последняя дельта, сборка ВМ
sudo d2g job sync <job>
sudo d2g job finish <job> --flavor STD3-4-8 --network <сеть> --sg default --key <ключ> [--name web01]

# 5. убрать агента с источника
sudo d2g agent uninstall web01
```

`job finish` дожидается, пока приёмник отпустит том, отключает том, делает его загрузочным, ставит
свойства образа (из `props.json` источника или из `/etc/os-release`) и создаёт ВМ с загрузкой с
тома в той же зоне. `job delete` отпускает и удаляет том.

Если у приёмника в нужной зоне нет свободного места под тома (по умолчанию 20 томов на приёмник),
`job new` сам создаёт новый приёмник. Его можно создать и заранее:

```bash
sudo d2g receiver add [--az PA2] [--flavor STD3-8-8] [--fip <id>|auto]
sudo d2g receiver list
sudo d2g receiver delete rx1
```

Новый приёмник поднимается примерно за 1,5 минуты: том из образа, ВМ, cloud-init скачивает бандл
у оркестратора, `unique-boot.sh`, регистрация, первый отчёт.

## Несколько проектов

Один оркестратор переносит ВМ не только в свой проект («этот проект», `home`), но и в другие
проекты облака: для каждого добавляется служебная учётка этого проекта. Учётки хранятся только на
ВМ оркестратора (`/etc/d2g/targets/<имя>.openrc`, права 600) и при добавлении проверяются теми же
пробами, что в мастере (том 1 ГБ и группа безопасности создаются и удаляются).

| Способ | Как работает | Что нужно в проекте | Когда |
|---|---|---|---|
| **Передача тома** (`transfer`) | диск принимается в проекте оркестратора (`rx0` или его приёмники); при «Создать ВМ» том отключается, передаётся в проект (Cinder volume transfer: запрос учёткой оркестратора, приём учёткой проекта), и ВМ создаётся там | только служебная учётка | проекты того же региона; ни приёмников, ни FIP в проекте |
| **Свой приёмник** (`receiver`) | оркестратор учёткой проекта создаёт в нём приёмник (cloud-init) и группу безопасности `d2g-receivers`; тома создаются, принимаются и превращаются в ВМ в этом проекте | учётка и сеть; FIP для приёмника, если источники за интернетом | другой регион; данные не должны появляться в проекте оркестратора; источник рядом с проектом |

В режиме «свой приёмник» приёмник ходит к оркестратору по его **публичному адресу** (FIP
оркестратора обязателен); оркестратор сам открывает 443 от адреса роутера сети приёмника в своей
группе `d2g-ctl` (если она подключена к его ВМ). Агенты идут к такому приёмнику по серому адресу
(источник в той же сети или за Direct Connect этого проекта), по его FIP или через оркестратор, если
у приёмника есть FIP.

Добавить проект — вкладка «Проекты» → «Добавить проект»: учётка → «Проверить учётку» → настройки из
списков этого проекта (зона, сеть, группы безопасности новых ВМ; для своего приёмника — флейвор,
тип томов, ключ, FIP, откуда приходят источники) → «Сохранить». В «Новом задании» выбирается «Куда
переносить», форма «Создать ВМ» показывает флейворы, сети, группы безопасности и ключи того проекта.

То же в командной строке:

```bash
sudo d2g target add kz --title "VK Cloud KZ" --mode receiver --openrc /tmp/kz.openrc \
  --az QAZ --network dmz-kz --rx-flavor Standard-4-8 --allow 10.0.0.0/24 --vm-sg default --vm-sg ssh
sudo d2g target add client-a --mode transfer --openrc /tmp/client-a.openrc --network client-net
sudo d2g target list | check NAME | set NAME [...] | delete NAME
sudo d2g job new web01 --target kz
```

## Веб-интерфейс

Интерфейс работает в том же сервисе оркестратора и открывается по его адресу:
`https://<FIP оркестратора>/`. Агенты и приёмники ходят на тот же порт 443 по имени
`ctl.<id>.d2g`, а браузер приходит по IP и получает интерфейс со своим сертификатом.

Вкладки:

| Вкладка | Что на ней |
|---|---|
| Обзор | сколько ВМ подключено, сколько заданий, что синхронизировано, приёмники; текущие проходы с прогрессом; последние операции |
| Исходные ВМ | «Добавить ВМ» → готовая команда установки (кнопка «Скопировать»); ОС, ядро, диск, модуль, путь до приёмника, адрес, последний отчёт; «Проход», «Новый токен», «Удалить агента», «Отключить» |
| Задания | «Новое задание» (ВМ, тип тома, зона, расписание дельт); прогресс; «Дельта», «Расписание», «Создать ВМ» (флейвор, сеть, группы безопасности, ключ — списки из облака), «Удалить» |
| Приёмники | состояние, адреса, тома, нагрузка; «Добавить приёмник», «Удалить» |
| Журнал | операции интерфейса с живым логом; журнал событий (кто и что сделал: `admin` — командная строка, `ui:<имя>` — интерфейс, агенты, приёмники) |
| Настройки | текущие параметры оркестратора (меняются командой `d2g setup`) |

Изменения из интерфейса выполняются той же командой `d2g` от root (только проверенные значения,
без shell), поэтому интерфейс и командная строка ведут себя одинаково. Долгие операции (тома, ВМ,
приёмники) идут в фоне, их лог виден на вкладке «Журнал».

### Безопасность без домена

| Мера | Как |
|---|---|
| Свой сертификат интерфейса | одиночный самоподписанный сертификат (не CA) на IP оркестратора. `d2g setup` печатает его отпечаток SHA-256: при первом входе его сверяют с отпечатком в браузере или импортируют сертификат в систему. CA агентов в браузер не ставится — он мог бы подписать любой сайт |
| Доступ по подсетям | интерфейс открывается только из `--ui-allow` (настоящий адрес клиента приходит от nginx по PROXY protocol); остальным — 403. По умолчанию список пуст, интерфейс закрыт |
| Пароль | хэш scrypt; 5 неверных попыток → пользователь и адрес блокируются на 5 минут |
| Второй фактор | TOTP (Google Authenticator и т. п.), `d2g admin totp ИМЯ` |
| Сертификат администратора (по желанию) | `d2g admin cert ИМЯ` выпускает `.p12` для браузера, `d2g setup --ui-mtls on` делает его обязательным: без него интерфейс не откроется |
| Сессия | cookie `Secure`, `HttpOnly`, `SameSite=Strict`; выход после 30 мин бездействия, не дольше 12 ч |
| Запросы | каждое изменение — с CSRF-токеном в заголовке; строгая CSP без inline-скриптов и стилей, запрет встраивания во фреймы, `no-referrer`, `no-store` |
| Журнал | входы, неудачные попытки и все действия пишутся в журнал событий |

Ограничение: пока сертификат не импортирован, браузер показывает предупреждение. Если отпечаток
не сверить и просто принять сертификат, при атаке «посередине» на первом входе пароль можно
перехватить. TOTP и сертификат администратора делают такой пароль бесполезным.

Доступ через SSH-туннель тоже работает и не требует открывать 443 для адреса администратора:

```bash
d2g setup --ui-allow 127.0.0.1/32
ssh -L 8443:127.0.0.1:443 ubuntu@<оркестратор>      # затем https://localhost:8443/
```

### Администраторы

Первого администратора создаёт мастер. Остальные — на ВМ оркестратора:

```bash
sudo d2g admin add anna             # пароль от 12 символов
sudo d2g admin totp anna            # второй фактор: секрет и ссылка otpauth:// для приложения
sudo d2g admin passwd anna | delete anna | list
sudo d2g admin cert anna            # сертификат для браузера (.p12), затем d2g setup --ui-mtls on
```

Если интерфейс открыт по FIP, порт 443 в группе безопасности ВМ оркестратора должен быть открыт
и для адресов администраторов (мастер делает это сам, если отмечено).

### Из другой площадки: VK Cloud KZ → VK Cloud RU (17.10.2026)

Источник `d2g-kz-src1` в KZ: Standard-4-8, Ubuntu 24.04, диск 100 ГБ ceph-ssd, PostgreSQL + pgbench и
40 ГБ несжимаемых данных. В интернет выходит через роутер (SNAT), FIP у источника нет (SSH через
отдельный jump с FIP). Приёмник — `rx0` на ВМ оркестратора в RU (STD3-4-8). Агент сам выбрал путь
`ctl`: серый адрес приёмника из KZ недоступен.

| Проверка | Результат |
|---|---|
| Первый проход, 8 потоков | 1668 с (28 мин): из 100 ГБ диска по проводу 35,3 ГиБ (COW-файл 10 ГБ и пустые блоки не передаются), 21 МиБ/с, 0 повторов; приёмник загружен на 21 % |
| Дельта +5 ГБ: 8 / 24 потока | 16 / 12 МиБ/с — больше потоков не помогает |
| Канал без нашего протокола (поток по SSH на ВМ оркестратора) | через SNAT роутера KZ: 1 поток 12–15 МиБ/с, 8 потоков вместе 6 МиБ/с; **через FIP (jump-хост): 31 МиБ/с** |
| Последняя дельта (pgbench) | 392 МиБ, 236 с (3,9 мин) — почти всё время чтение диска 100 ГБ (433 МиБ/с) |
| ВМ в RU из тома (`job finish`) | загрузилась; PostgreSQL восстановился, последняя метка в файле и в базе = момент снапшота, `amcheck` чистый, инвариант pgbench сходится; MD5 всех 5 файлов с данными (40 ГБ) совпадают с источником; агент на копии выключен |

Вывод: из KZ упор в выход источника в интернет через роутер (сетевой узел), а не в приёмник или
протокол. Источник с собственным FIP выходит примерно вдвое быстрее. Если переносить много ВМ из
одной площадки, стоит выдавать источникам FIP на время переноса или планировать время по
скорости SNAT (~15–20 МиБ/с на источник; один источник на 100 ГБ с 35 ГБ данных — около 30 минут).
Дельта читает весь диск, поэтому на больших дисках её время определяет скорость чтения, а не канал.

Замечание: при первой загрузке ВМ `unattended-upgrades` обновил nginx и перезапустил его посреди
передачи. Передача через оркестратор пережила это за счёт повторов (7 повторов частей).
