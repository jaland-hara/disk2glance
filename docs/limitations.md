# Ограничения

Что disk2glance не поддерживает, почему и можно ли это исправить. Термины — в [README](../README.md#термины), оглавление документации — в [docs/README.md](README.md).

Оценка «устранимо» означает, что ограничение снимается доработкой disk2glance.
«Неустранимо» означает, что оно следует из самого Glance, ядра или dattobd, и
обойти его можно только другим способом переноса.

| # | Ограничение | Причина | Устранимо? |
|---|---|---|---|
| 1 | Через снапшот переносятся только ext3/ext4/xfs (на разделе или линейном LV) | dattobd поддерживает эти ФС | частично (см. btrfs) |
| 2 | LVM: только линейные LV, VG на одном диске; thin, raid, striped не поддерживаются | соответствие экстентов строится по `dmsetup table` линейных сегментов | линейный LVM **сделан в 0.3**; остальное частично |
| 3 | mdraid не поддерживается | своё сопоставление блоков и метаданные на каждом диске | да, но требуется редко |
| 4 | dm-crypt/LUKS не поддерживается | снапшот видит расшифрованные данные | практически нет |
| 5 | btrfs не поддерживается | dattobd не работает с btrfs | нет (только другим способом) |
| 6 | ФС на целом диске без таблицы разделов | не реализовано | **да**, несложно |
| 7 | Один диск за запуск, снапшоты разных дисков не одновременны | не реализовано | **да** |
| 8 | Каждый запуск передаёт диск целиком (Glance и S3) | образы Glance неизменяемы | нет; при переносе через оркестратор повторные проходы передают только изменения |
| 9 | Один поток загрузки (~90–120 МиБ/с в VK) | API Glance: одна загрузка на образ | в Glance нет; **экспериментальный S3-режим** (0.5) |
| 10 | Нужен модуль под точное ядро исходной ВМ | модуль ядра собирается под конкретную сборку ядра | да, сборка в CI под все ядра |
| 11 | Secure Boot, kernel lockdown, ЗПС Astra блокируют модуль | неподписанный код ядра | да, но нужна перезагрузка исходной ВМ |
| 12 | Нужно свободное место на каждой ФС под COW-файл (10% или `--cow-mb`) | COW-файл dattobd размещается на той же ФС | частично |
| 13 | Только crash-consistent | снапшот блочного уровня ничего не знает о приложениях | **да**, хуками |
| 14 | Учётные данные хранятся на исходной ВМ | агент сам обращается к API | **да**; при переносе через оркестратор на исходной ВМ только сертификат агента |
| 15 | Только Linux x86_64 | сборки есть только для x86_64; для Windows нужен другой механизм | да |
| 16 | Пауза записи при создании снапшота: 1–3 с, под сильной нагрузкой до десятков секунд | dattobd замораживает ФС, пока записываются данные из кэша и создаётся COW-файл | **уменьшено в 0.3** (`sync`, `--cow-mb`); полностью нет |

Пояснения к каждому пункту приведены в следующих разделах.

## 1–5. Тома и файловые системы

**Как устроено сейчас.** Агент строит список «наложений»: какие байтовые диапазоны диска
нужно взять из снапшотов. Для обычного раздела это весь раздел, для LV — его экстенты
внутри PV. Всё остальное читается с диска как есть.

**LVM (п. 2). Линейный LVM поддерживается с 0.3** (проверено на типовой установке CentOS 7:
`/boot` на xfs, `centos-root` на xfs, `centos-swap`). Соответствие «сектор LV → сектор PV»
берётся из `dmsetup table`, подробности в [how-it-works.md](how-it-works.md#lvm).
Что не поддерживается и почему:
- *VG на нескольких дисках.* Образ Glance — это один диск, а LV, распределённый по двум
  дискам, невозможно поместить в один образ. Нужен одновременный перенос всех дисков в отдельные
  образы (см. п. 7). Устранимо вместе с п. 7.
- *thin pool / thin LV.* Блоки thin-тома распределяются через метаданные пула (свой
  B-tree в отдельном LV), а не линейно. Подставлять экстенты придётся по метаданным пула,
  которые сами меняются во время работы. Теоретически устранимо, практически сложно;
  обход — перенести в окно простоя.
- *LVM-raid, зеркала, striped.* Устранимо: у striped известна формула чередования, у
  raid1/зеркал каждая копия — линейный образ. Пока не встречалось в целевых установках.
- *Операции с томами во время переноса* (`lvcreate`, `lvextend`, `pvmove`) запрещены:
  метаданные LVM читаются как есть, и их изменение посреди переноса даст несогласованный
  образ. Это организационное ограничение.

**mdraid (п. 3).** Та же задача сопоставления, плюс у каждого члена массива свой
суперблок. В облачных ВМ встречается редко. Устранимо для RAID1; для остальных уровней
доработка нецелесообразна.

**dm-crypt/LUKS (п. 4).** Снапшот создаётся с расшифрованного устройства. Чтобы
поместить в образ зашифрованный раздел, пришлось бы шифровать поток заново ключом тома,
то есть агенту нужен мастер-ключ. Есть два выхода: перенести данные расшифрованными
(меняется модель безопасности, решает владелец данных) или перенести в окно простоя
обычным копированием. **В рамках живого переноса ограничение считается неустранимым.**

**btrfs (п. 5).** dattobd не поддерживает btrfs: btrfs сама записывает данные по
принципу copy-on-write и перемещает блоки, и механизм dattobd с COW-файлом на той же ФС
с этим несовместим. Альтернатива — штатный снапшот btrfs и копирование на уровне файлов,
то есть уже другой способ переноса (создание ФС заново). В целевых ОС (RED OS, Astra,
CentOS) btrfs почти не используется.

**ФС на целом диске (п. 6).** Например, `/dev/vdb` без разделов, смонтированный как
`/data`. Не реализовано, хотя dattobd создаёт снапшот любого блочного устройства.
**Простая доработка.**

## 7. Несколько дисков

Каждый запуск переносит один диск в один образ. Если на исходной ВМ несколько дисков (например
`/` и `/data`), снапшоты разных запусков снимаются в разное время, и данные на дисках
не согласованы между собой.
*Способ устранения:* создать снапшоты всех дисков подряд в одном запуске, затем загрузить их в
отдельные образы (последовательно или параллельно). В VK дополнительные образы превращаются
в тома (`openstack volume create --image`). **Устранимо, средняя сложность.**

## 8–9. Особенности Glance

**Каждый раз переносится весь диск (п. 8).** Образ Glance после загрузки изменить нельзя,
поэтому загрузить изменения в тот же образ невозможно. **Неустранимо:** disk2glance
остаётся простым инструментом «диск → образ Glance», инкрементальная репликация в его
задачи не входит. Время переключения определяется временем загрузки диска.

**Один поток (п. 9).** В API Glance нет загрузки по частям: на один образ один
`PUT .../file`. В VK из методов импорта доступны только `glance-direct` и `copy-image`
(без `web-download`), поэтому вариант «загрузить в S3 параллельно и импортировать в Glance
оттуда» тоже не работает. **Ускорить загрузку одного образа нельзя.**
*Обходные пути:* если у исходной ВМ несколько дисков, их образы можно загружать параллельно
(см. п. 7). С версии 0.5 есть экспериментальный режим через S3 ([s3-mode.md](s3-mode.md)):
диск передаётся в бакет частями в несколько потоков с повтором неудачных частей, а новая ВМ
собирается из S3 на временной ВМ-сборщике. На 300 ГиБ: 17,5 мин против ~44 мин через Glance.

## 10–11. Модуль ядра

**Модуль под конкретное ядро (п. 10).** Модуль ядра совместим только с той сборкой ядра,
под которую собран: `vermagic`, версии символов и адреса неэкспортируемых символов из
`System.map`. Собирать на исходной ВМ не нужно: сборочная ВМ дистрибутива собирает
модули под любые ядра из его репозиториев ([build-modules.md](build-modules.md)).
*Способ полного устранения:* CI по расписанию собирает модули под все ядра всех поддерживаемых
дистрибутивов. Для нестандартных ядер остаётся `install.sh --build` прямо на исходной ВМ.
**Устранимо организационно.**

**Secure Boot, lockdown, ЗПС Astra (п. 11).** Ядро не загружает неподписанные модули.
Модуль можно подписать собственным ключом, но ядро исходной ВМ должно этому ключу доверять:
- Secure Boot: регистрация ключа в MOK (`mokutil --import`), затем **перезагрузка** и
  подтверждение в консоли;
- ЗПС Astra: ключ добавляется в доверенные ключи digsig администратором исходной ВМ, обычно с
  обновлением initramfs и **перезагрузкой**;
- либо временно отключить защиту, тоже с перезагрузкой.

**Устранимо, но перезагрузку исходной ВМ не обойти**, поэтому это нужно планировать на окно
обслуживания до переноса. Сам перенос затем выполняется без остановки.

## 12. Свободное место под COW

dattobd хранит старые версии изменённых блоков в файле `.datto_d2g` на **той же** ФС;
так устроен драйвер. По умолчанию файл занимает 10% раздела. Если ФС почти заполнена,
снапшот не создастся. Если за время переноса изменится больше данных, чем помещается в
файл, снапшот перейдёт в состояние ошибки (рабочая ФС не пострадает, перенос придётся повторить).
*Что можно сделать:* задать размер COW-файла (`--cow-mb`, с 0.3), предупреждать в `--check`
о нехватке места (план) и выбирать время переноса с меньшей нагрузкой. **Убрать сам COW-файл
с этой ФС нельзя**, это архитектура dattobd.

## 13. Согласованность на уровне приложения

Снапшот блочного уровня фиксирует состояние «как после отключения питания». Журналируемые
ФС и СУБД с журналом восстанавливаются из такого состояния (проверено на PostgreSQL). Приложения без журнала
или с данными в памяти — нет.
*Способ устранения:* хуки `--pre-snapshot` / `--post-snapshot`, например `pg_backup_start`,
`FLUSH TABLES WITH READ LOCK`, остановка службы. Снапшот делается за 1–3 секунды,
поэтому пауза приложения будет короткой. **Простая доработка.**

## 14. Учётные данные на исходной ВМ

Сейчас пароль сервисной учётной записи хранится в `/etc/disk2glance/openrc` (600) на
переносимой ВМ до `--uninstall --purge`.
*Способ устранения:* передавать агенту токен с коротким сроком действия (`OS_TOKEN`) и адрес Glance вместо
пароля либо использовать application credentials с ограниченными правами, если облако их
поддерживает. **Простая доработка.**

## 15. Платформы

Сейчас только Linux x86_64. Для arm64 нужны сборки модуля и бинарников (dattobd сам по
себе переносим). **Windows** — отдельный агент на VSS: теневые копии томов плюс чтение
`\\.\PhysicalDrive0` с подстановкой томов из теневых копий, та же схема объединения потока.
Отдельная задача — vTPM и BitLocker
 при переносе Windows 10/11 в облако без vTPM.

## 16. Пауза записи при создании снапшота

Чтобы снапшот был согласованным, dattobd на мгновение замораживает ФС: ядро записывает на
диск изменённые данные из страничного кэша, dattobd выделяет COW-файл и включает перехват.
Всё это время запись приложений приостановлена. На простаивающей системе пауза 0,1 с, на RED OS и Ubuntu под умеренной
нагрузкой 1–3 с. На CentOS 7 с XFS на ceph-hdd под нагрузкой без ограничения скорости
пауза была 17–26 с.

Что сделано в 0.3: агент выполняет `sync` перед снапшотами, чтобы во время заморозки
записывать было почти нечего (пауза ~11 с в том же тесте), и появился `--cow-mb` для
уменьшения COW-файла (с 256 МиБ пауза ~6 с).

**Полностью убрать паузу нельзя:** без заморозки снапшот не будет согласованным. Её можно
только сокращать: переносить в часы низкой нагрузки, уменьшать COW, при необходимости
кратко останавливать запись самим приложением (п. 13).
